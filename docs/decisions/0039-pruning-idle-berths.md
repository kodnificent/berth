# 0039. Pruning idle berths: remove's sequence, judged again at each berth's turn, no deadline

Status: accepted

## Context
`berth prune --idle 7d` removes every berth unused for seven days as `berth remove` would, `pre-remove` included, and never touches the worktree's own files (design, Idle berths). A berth with a running container or a locked worktree is never idle, and `prune --idle` always checks every worktree it judges, where `list` may stop (0037). The guarantee "Idle pruning keeps the work" depends on all of it. Prune runs for minutes when hooks are slow, so a berth idle when the list is made may be used or started before its turn.

## Decision
- **Duration.** `--idle <duration>` or `--idle=<duration>` takes a positive whole number of days, hours or minutes: `7d`, `12h`, `30m`. Anything else, zero included, is a usage error that exits 1 before the registry is opened, so nothing is deleted.
- **Order.** Orphans go first, exactly as 0027 has them, under one registry lock. That lock is then released, and every berth that is not orphaned and whose worktree is not locked is judged.
- **Judging.** Last use is 0037's computation, but with no deadline on the worktree checks: four at a time, each `git status` taking as long as it takes, so a slow worktree delays prune instead of looking older than it is. Docker is asked once, as `list` does. A berth is idle when its last use is older than the duration and Docker says none of its containers runs. A berth whose last use is within the duration is not idle whatever else is unknown. One that would be idle but Docker couldn't be asked, or whose worktree `git status` failed on, is reported as unknown, kept, and makes prune exit 1.
- **Removing.** Each idle berth goes through the same function `remove` uses, `removeSequence`: refuse while `post-add` runs; run `pre-remove` in the worktree with `BERTH_PATH` set and no lock held, so it can run `berth status` or `berth env`; then take the worktree lock, the registry lock, check for outside use, quiesce (0026), plan again and tear down. Both locks are released before the next berth, so other berth commands run between berths. A failed `pre-remove` keeps that berth, prune goes on with the others and exits 1.
- **Judged again at its turn.** A berth that `berth remove` took during an earlier hook, or whose worktree now holds another berth, is skipped silently: no hook runs and no state is written for it. An earlier berth's `pre-remove` can also use, start or lock a later berth, so just before a berth's own `pre-remove` runs it is judged again in full, with fresh data and no cutoff: its worktree must be unlocked, no container of it may run, and its last use, every worktree change git sees included, must still be older than the duration. A berth that fails is kept and its `pre-remove` never runs. It is named on stderr with the reason and does not fail the command; unknown, as above, does.
- **After its `pre-remove`.** The hook may legitimately rewrite the worktree: stash, commit, save a dump. Worktree changes are therefore not checked again, since a stash or commit rewrites the index, the HEAD log and file times, and with them the evidence of earlier use. Under both locks, where no berth command can record a use, only what the hook can't stand for is checked: the worktree is still unlocked, no berth command recorded a use since the judgement before the hook, and no container of the berth's project is up, since one running after the hook means someone started it. Failing any keeps the berth as above. These checks come before quiescing, so a clone started by a `reset` after the list is never stopped for a berth that is then kept.
- **With no `pre-remove`.** Nothing can account for a change in the worktree, so under both locks the use measurement runs again in full, with no deadline and worktree changes included. A berth whose last use is now within the duration, or later than at the judgement before, is kept. This catches a commit or an edit made while prune waited for the worktree or registry lock that another `remove` or `prune` held.
- **Output.** `--dry-run` lists orphans and idle berths with what would be deleted, from the same judging, and runs no hook. Each entry in `--json` carries `reason` (`orphan` or `idle`) and `last_used` (0027). Without `--json`, an idle berth reads `Removed idle berth <id> (<worktree>), last used 9d ago:` followed by its items.

## Options considered
- **A separate removal path for prune:** two copies of the lock order and the `pre-remove` rules would drift, and a fix to one would miss the other.
- **Holding the registry lock for the whole prune:** `pre-remove` calling `berth status` would deadlock, and every other berth command would wait for every hook.
- **Judging once, from the list:** a berth started or edited during an earlier berth's hook would get its own `pre-remove` run and be torn down while in use.
- **Judging only after the hook, ignoring changes from when it started:** the index, the HEAD log's last entry and a directory's time are single timestamps; a hook that stashes or commits rewrites them, so a commit and an edit made before the hook would be lost and the berth pruned. A hook that stops the stack would hide the container someone started.
- **Rechecking after quiescing:** quiescing kills a running clone, so a berth reset after the list would lose its clone and then be kept anyway.
- **Counting worktree changes after the berth's own `pre-remove`:** any hook that writes into the worktree would make its berth unprunable.
- **`list`'s 1.5 s bound:** a worktree not checked in time keeps only recorded use, which reads older than the truth, and prune would delete a berth that was in use.
- **Go's `time.ParseDuration`:** has no days, and accepts `1h30m` and fractions that the design's `7d` doesn't need.

## Evidence
`e2e/prune_idle_test.go`: the dry run lists exactly what prune then deletes, orphans included; a pruned berth's tracked files, staged and unstaged changes, untracked and ignored files and a symlink survive byte for byte; a berth with a running container or a locked worktree is kept; a failing `pre-remove` keeps only its berth and exits 1; a `pre-remove` running `berth status` and `berth env` finishes within two minutes and its berth is pruned; a berth with no recorded use is judged by its creation; Docker unreachable reports each berth unknown and exits 1; a berth edited or started by an earlier berth's hook is kept; `add` after prune clones from main again; invalid durations delete nothing; prune without `--idle` runs no hook; hours and minutes work; a `git status` slowed to 3 s still sees an edit. `e2e/prune_idle_own_hook_test.go` covers a berth whose `pre-remove` saves into its own worktree and is still pruned. In `e2e/prune_idle_window_test.go`, with a slow earlier hook: a later berth committed to and edited before its turn is kept and its `pre-remove`, which would stash, never runs; a later berth started before its turn is kept and its `pre-remove`, which would stop the stack, never runs; a later berth whose worktree is locked before its turn is kept; a later berth removed before its turn runs no hook, leaves no post-add lock, and prune exits 0. `e2e/prune_idle_lock_wait_test.go` keeps a berth with no hook that gets a commit while another process holds its worktree lock. In `e2e/prune_idle_review_test.go`: a berth whose `git status` fails is reported unknown and kept, prune exits 1 and another idle berth is still pruned; a berth whose own `pre-remove` starts one of its containers, or runs `berth status` without `BERTH_PATH`, is kept with its files, container and volume, named on stderr, and prune exits 0.

Not covered: with a `pre-remove`, a change a user makes in the berth's worktree, or a container someone starts and stops again, from the judgement before the hook until the teardown, since neither can be told apart from the hook's work; that window includes any wait for the locks. With no `pre-remove`, a change between the measurement under the locks and the teardown, a window of one `docker ps`, quiescing and planning. In both cases, a container started after the last check, which is removed with the berth.

## Undoing it
`runPrune`, `pruneIdle` and `removeIdle` are in `internal/cli/prune.go`; `removeSequence` in `internal/cli/remove.go`; `measureUse` in `internal/cli/lastused.go`. Dropping `--idle` means deleting `pruneIdle` and `removeIdle`; orphan pruning doesn't depend on them.
