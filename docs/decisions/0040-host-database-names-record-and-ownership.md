# 0040. Host databases: names, the record and ownership

Status: accepted

## Context
On a host MySQL server every worktree shares main's databases (design, Per-database control). A berth gets its own databases next to main's, under its own prefix or name, and `remove`, `prune` and `reset` must drop only what is the berth's, even after the config or main's `.env` changes, with the server down, or for a berth made before berth managed databases. The design guarantees that no berth's prefix begins another berth's prefix or a source database's name, that every exact name a berth gets is unique on the server, and that no credential berth reads is stored or printed. This record covers how berth talks to the server, how names are chosen, what the record holds and what a berth owns. Copying data is in 0043, seed files and `command` in 0045, and snapshots in 0046.

## Decision
- **Client:** berth speaks the MySQL protocol itself with `github.com/go-sql-driver/mysql`, pure Go, in `internal/mysql`. It connects with a 10 second timeout, TLS when the server offers it, and one connection. The driver's own logging is silenced, and every error has the user and password replaced before berth shows it, since the server names the user on access denied.
- **Server and login:** `from = "env:<PREFIX>*"` reads `<PREFIX>HOST`, `<PREFIX>PORT` (3306 when unset), `<PREFIX>USERNAME` (or `<PREFIX>USER`) and `<PREFIX>PASSWORD`. `add` reads them from main's `.env`; a missing host or user exits `5` naming the file, `from` and the keys. The prefix key must be set and non-empty in main's `.env`, or `add` exits `5` naming `prefix`.
- **Segment:** the berth's part of every name is its `{name}` with each run of characters other than letters and digits turned into one underscore, none at either end, so it never holds two underscores in a row. A prefix is main's prefix, the segment and `__`. Since a segment never contains `__` and never ends in `_`, no berth's prefix can begin another's built from the same main prefix.
- **Length:** with a prefix, the segment is cut so main's prefix, the segment, `__` and the longest key fit MySQL's 64 characters, and to 40 at most; when that leaves fewer than 8 characters, `add` exits `5` naming `prefix`. Without a prefix a name is the database, `__` and the segment; when the whole would pass 64, the database's name is cut and ends in `_` and 8 hex characters of its SHA-256, so two databases that share their start still get names of their own.
- **Choice under the lock:** in provision's candidates loop, under the registry lock, berth lists the server's databases again and takes the first of the segment, then the segment with `_2`, `_3` and so on, that is free. A prefix is taken when any database on the server starts with it (a source's, another berth's or a removed berth's leftovers), when another berth recorded on the same server has a prefix that begins it or that it begins, or a database name it begins. Without a prefix, a name is taken when the server has it, another berth on the server recorded it or it falls under another berth's prefix. A database listed after the berth was made gets its name on a later `add` by the same check: the name its segment gives when free, else the first of the berth's other candidates that is; an existing entry keeps its recorded name. At most 1000 candidates are tried, so the lock is never held for ever; past that `add` exits `1` and creates nothing. The choice is saved in the record by the registry before any `CREATE DATABASE`, so a crash after it leaves berth knowing the names, and a berth that has a record keeps its segment and prefix on every later `add`.
- **Sources:** with a prefix, main's databases are the server's databases under main's prefix, apart from those under any prefix berth recorded on that server and those whose part after main's prefix holds `__`, which only a berth's names do, unless the config lists that key by name. Each gets the strategy of its own key, else the matching `*` pattern with the most literal characters, else `default` (`skip` when unset). A listed key is created even when main doesn't have that database yet. Patterns need a prefix: without one, `"*"` would match every database on a shared server, so the config is refused with exit `5`.
- **Record:** `mysql` in the berth's registry record holds the server's host and port, the env key prefix, the segment, the berth's prefix and its key, and for each database its key, source, target, strategy, the env keys naming it in main's `.env`, its status and its size when made. Never a user or password. `none` databases are recorded with the source as target so `status` and `doctor` see them, and are never the berth's to drop.
- **Ownership:** a berth owns a database when it is under the recorded prefix, or the record names it as a target with a strategy other than `none`, and it is never a recorded source. `remove` and `prune` list every database on the recorded server the berth owns, as `database` items between images and files, and drop them. Nothing else on the server is ever listed.
- **Login for teardown:** `remove` and `prune` never read main's `.env` or the config's `[state.mysql]`. They read the login under the recorded env prefix from the berth's own `.env`, cloned from main's at `add`, and failing that from the environment berth runs in. An orphan whose worktree is gone has no `.env`, so `prune` keeps it, exits `1` and says to export the keys. When the server can't be reached or refuses the login, nothing is deleted and the record is kept, so running again finishes; a database that fails to drop stays in the record, and the berth's `.env` is kept while one does, since the retry reads the login from it.
- **reset:** reads main's `.env` under the recorded env prefix and refuses with exit `1`, dropping nothing, when it names another server than the recorded one, before any other check; once the volume checks pass too, it drops everything the berth owns there and creates its `fresh` databases again, empty. `add` refuses the same way, as it does when the config switched between having a prefix and not.
- **Env:** `managedEnv` writes the recorded prefix to the recorded prefix key, and each recorded database's target to the keys that named its source in main's `.env`, so `status`, `env` and `exec` need neither the server nor main's `.env`. The server's own keys are never rewritten and the login is never written.
- **doctor:** in a berth, the check for a key still naming a source leaves out the server's keys and the prefix key, so a login that happens to equal a database's name is never printed.

## Options considered
- The `mysql` client in a helper container: a `docker run` per query is slow, and reaching a server on the host's loopback from a container differs between Docker Desktop and native Linux.
- The host's `mysql` client: often not installed, and passing the password safely to it needs a temporary option file.
- Storing the login in the record: the design forbids it, and the record lives outside the repository where nothing else protects it.
- Reading the login from main's `.env` in `remove` and `prune`: the design keeps cleanup working with a broken main `.env`, and the berth's own copy is right there. Only an orphan lacks one, and the shell is a place the user controls.
- Hyphens or a hash in names: MySQL needs quoting for hyphens, which every app then gets wrong, and a hash on every name hides which berth a database belongs to.
- Recording only the prefix: databases made without one would have nothing to find them by, and a `none` database must be told apart from one berth made.
- Checking prefixes only against the registry: a removed berth's leftovers and databases made by hand would be adopted, and dropped with the next berth.

## Evidence
`e2e/host_databases_test.go`, `e2e/host_databases_names_test.go` and `e2e/host_databases_lifecycle_test.go` run against a MySQL 8.4 server in Docker published on a host port. They cover the naming guarantee with a prefix (berths `feat`, `feat-x` and `feat-x-y`) and without one, a long branch name, a prefix or an exact name already on the server being passed over, `skip` and `none` databases, `remove` dropping databases the app created under the prefix, `remove` with the server down keeping the berth until retried, `remove` from the record alone (config changed, then deleted, with main's `.env` unreadable), `reset` refusing when main names another server, a berth recorded before berth managed databases being removed without dropping anything, an orphan pruned with the shell's login, and a walk of the state directory, the managed block and every command's output for the user and password. A fuzz test in `internal/names` fails when a segment may end in `_`, and unit tests in `internal/registry` and `internal/cli` cover ownership and names recorded by another berth.

## Undoing it
The client is `internal/mysql`; segments and names are in `internal/names/database.go`; the choice, creation, env, teardown, reset and doctor checks in `internal/cli/databases.go`; the record type in `internal/registry`. Records keep `mysql` once written, and older code ignores it, so reverting leaves those berths' databases on the server with nothing to drop them: drop them by the recorded prefix and names first. Moving to another client only touches `internal/mysql`.
