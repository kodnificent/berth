# 0042. SQLite copies: a clone under SQLite's own read locks, taken by hand

Status: accepted

## Context
`[state.sqlite] files` lists database files in the worktree. Each berth gets a consistent copy of each, never a file torn by a write in progress, instantly where the filesystem has copy-on-write (design, State cloning), and cloning never changes or loses main's data (design, Guarantees). Main's app may be writing while `add` or `reset` copies, in rollback-journal or WAL mode. `remove` must delete the berth's copies and nothing else, and `status` must list each file.

## Decision
- **Locks, taken by hand:** berth opens main's files read-only and takes SQLite's own POSIX advisory locks with `fcntl`, at the byte offsets SQLite's unix VFS uses: SHARED on the database file, through the PENDING byte as SQLite does, and for a WAL database shared locks on the wal-index's first two reader slots (`-shm` bytes 123 and 124). A listed path that is a symlink in main is resolved first, since SQLite keeps the WAL, the `-shm` and its locks beside the file the link leads to. It waits up to 30 seconds for either, copies the files while it holds them, and releases them straight after. It opens nothing of main's for writing, creates nothing beside it and runs no SQLite code against it, so it never checkpoints, recovers, rolls back or deletes anything of main's.
- **Rollback-journal databases:** no writer can commit while SHARED is held, so the database file is one committed state. A `-journal` beside it is copied too: one a crashed writer left is hot, and the copy's first open rolls it back, as main's would; one a live writer is filling holds the original pages of a file it can't yet write, so rolling it back in the copy changes nothing. While SHARED is held, main's writers wait and then fail with `database is locked` once their busy timeout passes, and once a writer holds PENDING, main's readers fail the same way. On copy-on-write that lasts a millisecond or two, and `add` prints how long. A byte copy lasts as long as the bytes take, so before one starts, with the locks taken and copy-on-write just refused, `add` names the file and says that main's writes to it, and reads queued behind a waiting write, wait and then fail with `database is locked` until the copy ends.
- **WAL databases:** the database file and its `-wal` are copied, never the `-shm`, so the copy's first open rebuilds its index from the WAL. Writers never wait. Every checkpoint takes the first reader slot exclusively before it writes WAL frames into the database file, so while berth holds it shared the file holds still. A writer starting the WAL again from the top with a new salt, and `wal_checkpoint(TRUNCATE)`, both take reader slots 1 to 4 exclusively, so while berth holds slot 1 the WAL is never rewritten or cut: writers append instead. A copy that read the start of a WAL which was then rewritten or truncated would replay those old frames over a database file that already holds later pages, a state main never had that `integrity_check` still passes. With the WAL only growing, the copied file and WAL recover to a whole commit at or after the moment the locks were taken; a torn tail of the WAL fails its checksum and is dropped. As a second line, berth compares the WAL's 32-byte header, which holds its salts, before and after the copy and copies again when it changed. Ten attempts that each saw main's WAL open or change under them fail the copy rather than record it ready. SHARED also stops main's last connection from checkpointing and deleting its WAL on close while the copy runs. When main has no `-shm`, no connection has the WAL open and nothing can checkpoint; berth copies without the reader lock and checks afterwards that no `-shm` appeared, copying again if one did.
- **Copy-on-write:** `fclonefileat` on macOS, `FICLONE` on Linux (btrfs, XFS), from the descriptor the locks are held on, which stays open until the copy is done, since closing any descriptor of a file drops every POSIX lock the process holds on it. Where neither works, the bytes are copied from that same descriptor, and `add` first says so, with what main's app meets meanwhile, and warns when the copy would leave less than `[clone] min_free`.
- **Where locks don't reach:** POSIX locks are only as good as the filesystem that carries them. Docker Desktop's bind mounts carry none between the Mac and a container, either way, so when main's app writes the database from a container through a bind mount, berth's locks don't hold it off and the copy may be torn. On native Linux a bind mount is the same file under the same kernel, so the locks should hold; that is unmeasured.
- **Where it runs:** in `add` and `reset` themselves, under the worktree lock, after the berth's files and before volume clones start, not in the background clone process.
- **Record:** each listed file is an entry in the berth's record, `sqlite`, with its path, whether berth owns the copy (`own`), the directories berth created for it, strategy, status, size and time. `own` and `cloning` are saved before anything is written, so a killed copy leaves a file berth knows is its own. `status` reports a `cloning` entry as `failed` when no berth command holds the worktree lock, and the next `add` or `reset` copies it again. `status --wait` waits for the worktree lock while an entry is `cloning`, then reads the record again. `list` counts each copy at its recorded size in the berth's disk use, as it does databases (0022, 0040).
- **Ownership:** a copy berth wrote is the berth's, with SQLite's own files beside it, `-wal`, `-shm` and `-journal`: a WAL left beside the next copy would be replayed into it. A file the berth already had, or its sidecars, is never overwritten: the entry is `failed`, saying so, and `add --wait` exits `4`. A listed file main lacks is reported on stderr and recorded `ready` with `source_missing`, and the berth gets none; a later `add` tries again.
- **Only through real directories:** berth deletes a copy, or writes one, only when every directory on its path inside the worktree is a real directory. A branch that tracks a symlink where berth made a directory, say `database -> ../main/database`, replaces berth's directory on checkout without a word, since the copy in it is ignored, and the copy's path then leads into main. Berth then deletes and writes nothing there: `remove` and `prune` report it, keep the record and exit `1`; `reset` records the entry as `failed` and reports it, never as a file main lacks. A directory berth made is removed only when it is still a real, empty directory.
- **remove:** each owned copy that git doesn't track is an item of kind `sqlite`, after databases and before files, deleting the file and its sidecars; the directories berth created for it go too when that leaves them empty, so a file anyone else put there keeps them.
- **reset:** every owned copy, whether or not the config still lists it, is marked `cloning` and saved, deleted with its sidecars and copied again; a listed file the berth lacks is copied. Its dry run, text and JSON list each copy it discards as kind `sqlite`, `name` and `target` its path.
- **Config:** each entry must be a relative path inside the worktree, and none may also be under `[files] clone`, which copies files as they are; either exits `5` naming `state.sqlite.files`.

## Options considered
- The SQLite online backup API: consistent and needs no reasoning about WAL, but it writes a new file page by page, so the copy shares no blocks with main and takes time and disk in proportion to the database even on APFS.
- `VACUUM INTO`: the same objection, and it also rewrites the database.
- A plain clone with no lock: `clonefile` gives no atomicity guarantee against a writer, and nothing stops a checkpoint rewriting the file mid-copy.
- A read transaction through `modernc.org/sqlite`: on macOS its connections took no POSIX locks at all. With it holding a read transaction, `fcntl(F_GETLK)` from another process saw no lock on the database, the system `sqlite3` committed into a rollback database and checkpointed and truncated a WAL one. Opened read-write it also checkpointed main's WAL into main's file and deleted the WAL and `-shm` when it closed as the last connection.
- SQLite itself through cgo (`github.com/mattn/go-sqlite3`): its locks are real, but every release would need a C toolchain for each platform it is cross-compiled for, and a reader must still open the `-shm` read-write and may run recovery into it.
- `github.com/ncruces/go-sqlite3`: SQLite through WebAssembly with its own VFS, whose locks would need the same checking against the system `sqlite3`, for a single read lock berth can take in a few lines.
- `BEGIN IMMEDIATE` plus a checkpoint, then cloning only the database file: it writes main's file and stops main's writers in WAL mode too.
- Copying in the background clone process: the copy-on-write case is instant, and that process is built around Docker volumes and pausing containers. A large database on a filesystem without copy-on-write makes `add` wait; moving it to the clone process is the way out if that matters.
- Recording the copy's device and inode and deleting only a file that still matches: the real-directory check already keeps every deletion inside the worktree, where the file at the copy's path is the berth's whatever its inode, and an app that replaces its database file by rename would leave a copy berth could never remove.

## Evidence
`e2e/sqlite_test.go` copies under write load, in rollback and WAL mode, with a writer committing a ledger and its running total every 5 ms: three berths each, and every copy passes `PRAGMA integrity_check`, keeps the ledger summing to its total and holds every row committed before `add`. It also covers `add`, `reset`, `remove` and `status` for the copies. In `e2e/sqlite_blocks_test.go`, `F_LOG2PHYS_EXT` gives the same physical block for main's file and the copy on APFS.

`e2e/sqlite_locks_test.go`, with `BERTH_TEST_SQLITE_HOLD` keeping berth's locks for three seconds after the copy: the system `sqlite3` gets `database is locked` committing into a rollback database, and `PRAGMA wal_checkpoint(TRUNCATE)` reports busy and main's file is unchanged; both failed with the `modernc.org/sqlite` driver holding the read. Writing nothing of main's: a WAL database whose WAL holds commits, with nothing else connected, has its database, `-wal` and `-shm` byte for byte as before after `add` and `reset`, and the copy holds the WAL's rows; the driver changed the file and deleted both. A byte copy never torn by a WAL truncate (byte copy forced with `BERTH_TEST_SQLITE_NO_COW` and paused after its first 1 MiB of a 12 MB fully checkpointed WAL with `BERTH_TEST_SQLITE_PAUSE`, while main's app stays connected; main's `wal_checkpoint(TRUNCATE)` then reports busy and the copy dumps as main does; with slot 0 only, the truncate went through and the copy differed from main). A listed database that is a symlink with rows only in its WAL: unresolved, the copy had 50 rows of 70. The announcement before a byte copy. `remove` and `reset` deleting nothing through a symlink into main (a checked-out branch tracking `database` as a symlink into main; without the check both deleted main's database, WAL and `-shm`). `e2e/sqlite_sidecars_test.go` covers `reset` discarding the berth's leftover WAL, which fails when only the database file is deleted, and a file the berth already had being left alone. Unit tests in `internal/sqlite` and `internal/cli/sqlite_test.go` cover a file that is not a database, a WAL that keeps opening during the copy, interrupted copies and the directory rules.

The load test alone doesn't prove the locks: with copy-on-write forced off, byte copies passed 8 runs with the locks and 4 runs without them, and the `modernc.org/sqlite` driver, whose locks were never taken, had passed too. The lock tests above are what show a writer and a checkpoint really wait. Leaving out the `-wal` made every WAL load run fail, the copies holding 2000 to 3144 rows against 2160 to 3236 committed. A hot journal is copied and rolled back by reasoning from SQLite's journal format; no test covers it.

Docker Desktop 29.8.1 on macOS: a read transaction held by Python's `sqlite3` in a `python:3.12-alpine` container on a bind-mounted database showed no lock to the Mac's `fcntl(F_GETLK)`, and the Mac's `sqlite3` committed past it; a read held on the Mac didn't stop the container committing.

## Undoing it
The copy is `Clone` in `internal/sqlite`, its locks in `lock_unix.go` beside it; choosing files, the record, `status`, `reset` and `remove` are in `internal/cli/sqlite.go`, with the `sqlite` item in `internal/cli/remove.go`. Records keep `sqlite` once written and older code ignores it, so reverting leaves the copies in the worktrees with nothing to remove them: delete the paths the records list first. Another copy mechanism only replaces `Clone`.
