# 0043. Copying host MySQL databases with dump

Status: accepted

## Context
`dump` gives a berth a copy of main's database on the same host server (design, Per-database control). The copy must be a point-in-time copy with no torn writes, must never change main's data, and if anything of main's has to pause, berth says so first and the pause lasts only for the copy (design, Guarantees). It runs in the background like a volume clone: `add` returns, `status` shows progress, `add --wait` and `status --wait` wait, `kill -9` reads as failed and `add` again recovers, `reset` copies again (0021, 0029, 0036). A berth whose only state is host databases must copy them with no compose project and Docker not running. Berth reads the login from main's `.env` and never stores or prints it (0040).

## Decision
- **Copier:** berth copies through the pure-Go driver it already uses (`internal/mysql`, 0040), with three sessions to the server: one reads, one writes the target, one holds tables that need it. Nothing is installed, no client binary is run and no container is started.
- **Consistency:** the reading session is read-only, `REPEATABLE READ`, and reads every table inside one `START TRANSACTION WITH CONSISTENT SNAPSHOT`, so all of InnoDB is read as of one moment while main keeps committing; nothing of main's InnoDB is ever locked against writes. A base table of any other engine (MyISAM, MEMORY, ARCHIVE, CSV) has no snapshot, so the third session takes `LOCK TABLES … READ` on those tables only, before the snapshot starts, reads their rows itself and unlocks as soon as they are read, before any InnoDB table is copied. Reading them through the session that holds them matters: MyISAM queues a new reader behind a waiting writer, so a reader in another session would wait on a write that waits on the lock. The snapshot is taken while those tables are held, so they and InnoDB are the same moment.
- **Metadata locks:** the snapshot sets a savepoint as it starts and rolls back to it after each table, view and trigger it reads, as `mysqldump --single-transaction` does. That ends its shared metadata lock on what it has read, so a migration on main during a long copy waits at most for the table being read, and the queries that would queue behind a waiting migration never wait for the whole copy. A table altered on main before the copy reaches it fails the copy (the server reports the definition changed), and `add` again copies it.
- **Announcing:** before starting the clone process, `add` and `reset` list main's tables, name each table that will pause, its engine and its database, on stderr, and record those tables on the clone entry. The clone process lists them again when it copies; if a table would now need holding that wasn't named, such as one converted from InnoDB in between, it holds nothing and fails that database's copy, telling the user to run `berth reset`, which announces the pause. So berth never pauses anything of main's it didn't name first. Status records the held tables as `paused` and the time as `pause_seconds`.
- **Fidelity:** each table is created from `SHOW CREATE TABLE` (read with the source as the current database, so nothing in it names main's database), then filled with multi-row `INSERT`s of about 1 MB, bounded by `max_allowed_packet`. Values are read with `character_set_results = NULL` and written as hex literals with the column's own character set as introducer (`_latin1 X'e9'`), so no conversion and no escaping can change a byte; numbers are written as the server printed them, except `FLOAT`, which the server prints to 6 significant digits and is read as a double (`col + 0e0`) so writing it back gives the same bits; temporal values are quoted, with both sessions on `time_zone = '+00:00'`. A row whose hex form would pass half of the smaller of `max_allowed_packet` and the driver's 64 MiB is written differently: each value over 64 KiB is built in a session variable from raw chunks of at most 16 MiB (and a quarter of the packet) with `CONCAT`, then inserted through `CONVERT(@v USING <charset>)` for text, so any row main can return is copied. Generated columns are left out of the `INSERT` and computed again; invisible ones are listed by name. A table the server lists no columns for, as could happen if a server with `lower_case_table_names = 2` reported names in two cases, is matched case-insensitively when that finds exactly one, else fails the copy rather than copy it empty. The target session runs with `foreign_key_checks` and `unique_checks` off and `sql_mode = 'NO_AUTO_VALUE_ON_ZERO'`, as `mysqldump`'s output does. The target keeps main's default character set and collation.
- **Nothing points back at main:** a copy must never read or write another database, main's included, so every check fails closed: an object that only might reach out is left out, never copied.
  - **Engines:** only tables whose engine keeps its rows in the database itself are copied: InnoDB, MyISAM, MEMORY, ARCHIVE, CSV and MariaDB's Aria. Any other, such as MERGE (whose `UNION` names tables in other databases) or FEDERATED (rows on another server), is left out before anything is announced or held, so neither the announcement nor `LOCK TABLES` ever includes it. That listing is taken when the copy starts, and main may swap a table before the copy reaches it, so what decides is the table as created: right after creating each table, before any row is written, berth reads its engine from `information_schema.tables` and its definition as the server now prints it, and drops the berth's table, leaving it out, when the engine isn't on the list or the definition sets `UNION`, `CONNECTION`, `DATA DIRECTORY` or `INDEX DIRECTORY`, anything that can keep its rows or files outside the database.
  - **Foreign keys:** a table element of the printed `CREATE TABLE` whose `REFERENCES` names another database is dropped before the table is created, found with the lexer below rather than by line, since a constraint name may hold a newline. Table definitions come from the server, which prints a versioned comment such as `/*!50100 PARTITION BY … */` only when it runs it, so here the lexer reads its text as code and partitioned tables copy; should the lexer still fail on a definition, the table is created from the text as printed and the checks after creating it decide. After each table is created, berth reads its foreign keys from `information_schema.referential_constraints` and drops, with `ALTER TABLE … DROP FOREIGN KEY`, any whose referenced schema isn't the copy's, so the created table is checked whatever its definition's text looked like.
  - **Views and triggers:** berth reads each one's text with a small MySQL lexer, under the trigger's recorded `sql_mode` (the view's is printed under the copy's own, empty one): `--` comments (only when followed by whitespace or a control character, as the server reads them), `#` and `/* */` comments are dropped and read to where the server ends them; every whitespace character, `\v` included, separates; string literals are kept whole, with backslash escapes unless `NO_BACKSLASH_ESCAPES`; backtick names, double-quoted text (a name under `ANSI_QUOTES`, and counted as one otherwise) and bare names are names. An object with a name equal, ignoring ASCII case and trailing spaces, to any database on the server other than the copy's own, with or without a dot after it, is left out, as is one with any name holding a character outside ASCII: with `lower_case_table_names` 1 or 2 (the latter the default on macOS) the server folds names by its own collation, under which `maİn` is `main`, and Go's folding doesn't match it. So is one the lexer can't read to the end (a comment or quote never closed). Text inside `/*!…*/`, `/*M!…*/` or `/*+…*/` may or may not run, depending on the server's version, and read the wrong way a quote inside it would hide what follows, so an object holding one is left out rather than guessed at.
  - Views are created until each one's dependencies exist, and triggers in their action order under their recorded `sql_mode`, after the rows and without their `DEFINER`, so the user berth connects as can always create them; one that still can't be created, such as a view calling a stored function, is left out too. Stored routines and events are not copied, matching `mysqldump`'s defaults, and the copy says when main has any. Everything left out is named in the clone log, in `status` as the entry's `notes`, and by `add --wait`, and the database is still `ready`, so `post-add` runs and can recreate them.
- **Target:** the clone process drops and creates the target before the snapshot, only after checking the berth's record owns it (0040), so a target the record doesn't name, or a source, is never touched. The copy is written straight into the target: MySQL can't rename a database, and moving views and triggers across databases isn't allowed, so there is no staging database. A database whose copy hasn't finished is `cloning`, or `failed` after a crash, never `ready`, and `status` hints say to wait.
- **Process and state:** a copy is an entry in the clone state's `databases` list beside `volumes`, run by the same `berth __clone` process under the same lock (0021): volumes first, then databases. `add`, `reset` and the post-add hook wait on that lock as before. Recovery marks an unfinished copy failed without asking Docker; the server ends a dead process's sessions, and its snapshot and table locks with them.
- **Login:** a `.env` that doesn't parse is reported by file and line only, never with the parser's message, which quotes the value it stopped in. The clone process reads the berth's record for the server and env prefix, then main's `.env` as it is at copy time for the login, and refuses when that `.env` now names another server. The login lives only in memory: never in the clone state, the log, the arguments or the environment of the process, and every driver error is scrubbed of it (0040).
- **Progress:** `add` measures each source's data and index size with `information_schema_stats_expiry = 0`, so a table filled since the server's daily statistics still counts, and records it as `total`. The clone process records `copied` every 2 seconds: the size of each table done plus the share of the current table's estimated rows read. `progress` stays at most `0.99` while cloning (0029).
- **Disk:** the warning measures free space where the server keeps its data: `@@datadir` when the server is on loopback and that directory exists here; otherwise a loopback server runs in a container or VM, whose disk is a file on this machine, so the smaller of the home directory's disk and Docker Desktop's data disk is used. A server elsewhere can't be measured, and `add` says so. Copies are counted cumulatively, as volumes are (0022).
- **add and reset:** `add` copies a `dump` database with no copy yet or whose copy failed; one already made under another strategy holds the berth's own data, so `add` says so and leaves it to `reset`. `reset` takes the clone lock, refusing while a clone runs, marks every `dump` entry `cloning` with `reset` and saves the clone state before dropping anything, then drops what the berth owns, makes its `fresh` databases again and hands the same lock to the code `add` uses. Its dry run and JSON list the berth's databases whether or not the project has volumes.

## Options considered
- The host's `mysqldump` and `mysql` piped together: the most proven format, and `--single-transaction` gives the same snapshot. But many machines have only a server app (DBngin, Herd) with no client on `PATH`, the client's version must match the server's (`mysqldump` 8.4 against MariaDB, or 5.7 against 8.4, fails or warns), the password must go through a temporary option file, and a missing client would fail the copy with nothing berth could do. Holding non-InnoDB tables only would also need `--lock-tables` per table, which takes every table.
- `mysqldump` in a helper container: needs Docker, and a berth whose only state is host databases must copy with Docker not running; and loopback differs between Docker Desktop and native Linux (0040).
- `FLUSH TABLES WITH READ LOCK` around the start of the snapshot, as `mysqldump --master-data` does: briefly stops every write on the whole server, other projects' included, and needs `RELOAD`.
- A staging database renamed into place: MySQL has no `RENAME DATABASE`, and `RENAME TABLE` can't move views or triggers across databases.
- Escaped string literals instead of hex: escaping is unsafe in multi-byte sets such as GBK and SJIS, where a trailing byte can be a backslash.
- Matching qualified names with a regular expression: a comment or a vertical tab between a name and its dot slipped past it, and the copy then wrote into main. SQL text needs reading the way the server reads it.
- Comparing names under the server's own folding (`LOWER(? COLLATE utf8mb3_general_ci)`): exact for that server, but a query per name, and leaving non-ASCII names out fails closed with no chance of a mismatch; an app whose triggers use such names recreates them in `post-add`.
- Trusting the engine listed when the copy starts: a migration on main between that listing and the table's turn swapped a table for MERGE, and the copy then inserted main's rows into another database.
- Treating versioned comments in view and trigger bodies as code: when the server skips one, a quote inside it, read as code, would open a string that hides real names after it.
- Copying every table whatever its engine: a MERGE table's rows live in the tables its `UNION` names, so inserting into the copy wrote into main, behind the copy's own table lock.
- Rewriting a view's or trigger's references from main's databases to the berth's: the berth maps only some of the server's databases, a reference can't be told from a string literal or a column without parsing SQL, and a missed one writes into main. Leaving the object out and naming it fails safe, and `post-add` can recreate it.
- Holding every table's metadata lock until the copy ends: simpler, but one migration on main mid-copy then stalls every query on that table for as long as the copy runs.
- Pausing a table converted since `add`, unannounced, as a volume clone pauses a container started since (0020): the design asks berth to say so before a pause, and failing the copy costs only a `reset`.
- Keeping each object's `DEFINER`: creating an object for another user needs `SET_ANY_DEFINER` or `SUPER`, which an app's user rarely has.

## Evidence
`e2e/host_dump_test.go`, `e2e/host_dump_fidelity_test.go` and `e2e/host_dump_reset_test.go` run against a MySQL 8.4 server in Docker published on a host port. They cover the "State is consistent" and "The source is never harmed" guarantees under a session committing a row to each of two tables throughout (the copy passes `CHECK TABLE` with equal counts, main's other rows keep their checksums); no write to main slower than 1 s across a copy held open for 6 s; a MyISAM table named before its writes are held; an `ALTER TABLE` on a copied table finishing within seconds while the copy is held open; a copy with no compose file and `DOCKER_HOST` pointing nowhere; the password kept out of state, logs and output; `FLOAT` 51.507351, 16777216, 1.2345678 and the clipped maximum kept exact; rows larger than 32 MiB; triggers naming another database across a `--` comment, an empty `/**/`, a vertical tab, a `#` comment and backticks around a comment, none of which reach main; a MERGE table left out with no pause announced; a foreign key into another database dropped though its constraint name holds a newline; a table swapped for a MERGE table mid-copy left out, which fails with the check removed; a partitioned table copied; and `reset` copying again. Unit tests for the lexer, the literals and the definition checks are in `internal/mysql`, for recovery without Docker in `internal/volume`, and for the unannounced-pause refusal and the `.env` error in `internal/cli`. A spike against MySQL 8.4 copied a MyISAM table with a trigger, a view over a view, `POINT`, `JSON`, `BIT`, `YEAR`, `TIMESTAMP(3)`, a stored generated column and a latin1 column with identical `CHECKSUM TABLE` results.

## Undoing it
The copy is `Copy` in `internal/mysql/dump.go`, the lexer `lex` in `internal/mysql/lex.go`; what `add` and `reset` prepare, the clone process's side and status are in `internal/cli/dumps.go`; the `databases` list and recovery in `internal/volume`. Swapping in a client binary touches only `Copy`. Reverting leaves clone state files with a `databases` list, which older code ignores, and `dump` databases in records, which older code refuses in the config; drop the berths' copies by their recorded targets first.
