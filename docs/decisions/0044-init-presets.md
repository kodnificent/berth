# 0044. Init presets as data files

Status: accepted; amends [0032](0032-init-detection.md) by adding preset suggestions to what init writes

## Context
The design says framework knowledge comes from presets: data files shipped with berth, each naming the files that show it applies and the config it suggests. `init` applies every preset whose files it finds and writes its suggestions under a comment naming it; a suggestion a file in the repository confirms is active, the rest are commented with their reason. `--preset <name>` applies one and `--no-presets` none. A preset only adds config a person could have written, and the core names no framework. The design leaves the format, how confirmation is checked, and how preset suggestions meet detection's (0032) open.

## Decision
- **Where the knowledge lives:** TOML files embedded from `internal/preset/`, one per preset, loaded by `internal/preset/preset.go`. That package is the only code that handles a preset's content; it hands `initconf.Render` a resolved list of suggestions, already checked against the repository, and `initconf` renders them with no idea which framework they came from.
- **Format:** each file names `applies` (conditions that show the preset fits) and its suggestions: `[[env]]` keys, `[[ports]]` entries for a process outside compose, and an optional `[mysql]` table. Every suggestion has a `confirm` list and a `reason`. A preset's file name is its name, and the loader rejects unknown keys, so a typo fails `go test` rather than shipping a suggestion that never applies.
- **Conditions:** a list holds when every term holds. A term tests that a file exists, that a file matches a regular expression, that a key is in one of a file's named top-level JSON objects (so a package manager's overrides don't count as a dependency), that main's `.env` sets a key or holds one of some values, or that an env value isn't a host port main publishes (with a default standing in for an unset key, since an unset `DB_PORT` means 3306 to both the app and berth). The grammar is in `internal/preset/preset.go`. A suggestion with no `confirm` is never active, which is how `SESSION_DOMAIN` is always commented.
- **Why a condition, not a list of files:** confirmation is specific to a key. `DB_DATABASE_PREFIX` needs a config file reading it and main's `.env` setting it, because `[state.mysql] prefix` reads main's value and `add` exits 5 without it. `VITE_PORT` needs `vite.config.*` reading it, because a port the dev server doesn't read does nothing. `SERVER_PORT` needs `artisan serve` in `composer.json` or the key in `.env`.
- **Suggestions a file can't save:** a key main's compose files read stays commented however it is confirmed, as in 0032, since berth never changes those. A port named after a compose service stays commented, because the config loader refuses a `[ports]` name a service also has. `[state.mysql]` is active only when main's `.env` points at a MySQL server on this machine, by `DB_CONNECTION`, a loopback `DB_HOST`, a `DB_PORT` compose doesn't publish, and `DB_USERNAME`; a database in compose is cloned with its volume, so the table is written commented with that reason.
- **Merging with detection:** a key a preset writes, or reads as its port or database prefix, is removed from detection's suggestions, so it is written once, in the preset's block. Where detection found a template for that key, the template replaces the preset's generic value, because it comes from main's real value: `APP_URL=http://localhost:8000` with an active `serve` port becomes `http://{host}:{port.serve}`. Active preset ports join the port map detection reads, so values holding main's port follow the berth's. Commented ports don't, so an active value never names a port the file doesn't define.
- **Databases:** with a confirmed prefix the table lists `"*" = "dump"`, every database under main's prefix; without one, it lists the database `DB_DATABASE` names, since `*` needs a prefix. When `DB_DATABASE` isn't under the prefix, `*` would leave it shared with main while the file looked as if it isolated the berth, so the whole table is commented with that reason. An unconfirmed prefix stays commented inside a commented table too, so uncommenting the table never turns on a prefix main's `.env` doesn't set.
- **Keys that hold a database's name:** berth writes every key in main's `.env` whose value names a copied database (design, Per-database control), and `add` refuses a second writer. So a preset key or port whose value in main's `.env` equals the database `DB_DATABASE` names stays commented with that reason. Only that name can be checked: `init` doesn't connect to the server, so a preset key equal to another database under the prefix, such as a tenant's, isn't seen, and `add` still refuses it with exit 5, naming the key.
- **Order:** presets in name order. A key already written by an earlier preset is left out of a later one's suggestions, and only the first preset's `[state.mysql]` is written, so the file stays one TOML document.

## Options considered
- A preset as a Go function: every framework would be code, and the core-framework test would have nothing to enforce against.
- Applying a confirmed suggestion only when `.env` confirms it: `.env` showing a key doesn't show the app reads it; `DB_DATABASE_PREFIX` in `.env` with no reader would rename databases the app never derives from it. So confirmation is per key, and `.env` is only one kind of term.
- `fresh` as the default database strategy: it leaves an app with no tables until a `post-add` migrates it, and a preset can't know that command is safe to run. `dump` gives a working copy and never harms main (0043).
- Letting detection write the key and the preset skip it: detection knows nothing of whether a config reads the key, so the line would never go active.

## Evidence
`e2e/init_presets_test.go`: a Laravel repository's config under a comment naming the preset, passing doctor; a repository matching neither preset and `--no-presets` byte for byte against goldens from before presets existed; `--preset vite` applying only vite; a config giving each berth its own databases under the prefix, `REDIS_PREFIX`, `CACHE_PREFIX`, serve and Vite ports, against a MySQL 8.4 server with `app_central`, `app_1` and `shop`; a confirmed prefix active and an unconfirmed one commented with its reason; `APP_URL` written once. `internal/initconf/frameworks_test.go`: no code outside the preset loader names a framework, except `internal/envfile/buildtime.go`, which holds the bundler prefixes the design's Doctor section specifies for its `build_env` check. `e2e/init_preset_tables_test.go`: a commented table with an unset prefix, uncommented, passes doctor against the real `.env`; a preset key holding a copied database's name leaves a config `add` accepts. `internal/preset/preset_test.go`: an unknown name is refused; a named preset applies without its files; a port named after a compose service, a key compose reads and a database in compose stay commented; a database without a prefix is listed by name; a database outside the prefix and an unset `DB_PORT` compose publishes keep the table commented; a preset key holding a copied database's name is commented; a pnpm override doesn't apply the `vite` preset; an active value never names a commented port; every suggestion uncommented still loads.

## Undoing it
`--no-presets` is the behaviour without presets, byte for byte. Removing them deletes `internal/preset`, `suggestions.go` and the `Presets` paths in `initconf.Render` and `runInit`, and changes only what `init` writes. A config already written from a preset is ordinary config and keeps working.
