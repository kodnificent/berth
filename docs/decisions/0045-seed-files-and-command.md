# 0045. Seed files and the command strategy

Status: accepted

## Context
A database can start from a file or a script instead of main's live data (design, Per-database control): `{ from = "file:<path>" }` loads plain SQL or gzip, resolved in the main worktree, and `{ command = "<script>" }` runs the user's script. Both run in the background as `dump` does, with progress, `add --wait`, `status --wait`, recovery from `kill -9`, and `reset` (0043, 0036). The design left the config key and the variable names open and now states them: `{ command = "<script>" }`, `BERTH_SOURCE_DB`, `BERTH_TARGET_DB`, `BERTH_DB_HOST`, `BERTH_DB_PORT`, `BERTH_DB_USER`, `BERTH_DB_PASSWORD`.

## Decision
- **A seed file is the user's own code.** It comes from the user's own repository and is trusted as `command` and `post-add` are. Berth runs it as written with main's login and doesn't inspect what its statements do, so a seed that names another database reaches it, the same as running the file with the `mysql` client. The guards on `dump` (0043) are different: they protect main from a copy berth makes on its own, from objects the user didn't write for this purpose.
- **Reused path:** both strategies are `databases` entries in the clone state, run by the same `berth __clone` under the same lock (0021, 0043), `Strategy` being `file` or `command`. `prepareDumps`, recovery, `status`, `add --wait` and `reset` treat them as they treat `dump`, through `clonedStrategy`. A `ready` entry isn't redone by `add`, a failed one is, and `reset` marks every entry `cloning` before anything is dropped (0036). The target is dropped and created only after the record says the berth owns it (0040). The seed file's path and the command are kept in the record, written by `add`; `reset` refreshes them from the config when the strategy is unchanged, so a changed path or script takes effect on `reset` as a changed volume list does. The login is read from main's `.env` at load time, as for a dump, and is never stored.
- **Reading the file:** gzip is recognised by its first two bytes, not the name, and a truncated stream fails the load. A byte order mark at the start is skipped. A streaming scanner splits statements the way the `mysql` client does, holding one in memory at a time, at most 64 MiB, the most the driver sends in one: on the delimiter, which `DELIMITER` lines change, outside strings, quoted names and comments, with a backslash escaping inside strings unless the session has `NO_BACKSLASH_ESCAPES`, which is read at the start and again after any statement mentioning `sql_mode`. The text of `/*!...*/` is read as code, as the client reads it, and goes to the server unchanged, so the server decides by its version what runs. A file that ends inside a string or comment fails rather than running a truncated statement. Progress counts bytes read from disk against the file's size.
- **Running it:** one connection, with the berth's database as the default and no read timeout, since one statement may run for hours. The session is left as the server sets it, and everything the file sets, such as `foreign_key_checks` or `sql_mode`, is the file's business. Statements run in order and the first failure stops the load: the database reads `failed`, with the file, the line and the server's message, scrubbed of the login. Statements before it have run, and the next `add` or `reset` drops the target again. A statement that is only versioned comments the server skips gets "Query was empty" back, which isn't a failure.
- **Sizes:** a load's, a command's and a dump's reported size is measured after `ANALYZE LOCAL TABLE` on each of the target's tables with `information_schema_stats_expiry = 0`, since the server's figures lag a bulk load (16 kB reported for 9 MB loaded).
- **`command`:** berth drops and creates the target as for a dump, then runs the script with `sh -c` in the main worktree, with the source and target names and the server's settings added to its environment, never its arguments. Its output goes to `clones/<id>.command-<key>.log`, truncated each run; the entry records the path and `status` names it. Its exit status decides ready or failed. The script runs in its own session, so its own process group, under an outer shell whose arguments carry a random mark. The shell waits on a pipe until berth has saved its pid and mark in the clone entry, so no run exists that recovery can't find; if berth dies first the pipe closes and the script never starts. The log path is saved before the script starts, so a run killed at any point still has its log named. Whoever finds the clone process dead (`status`, `add`, `reset`, `remove`, through `Recover`, under the clone lock) stops that group first, with `SIGTERM`, then `SIGKILL` after 3 seconds, and waits for it to go, before the entry reads `failed` and before anything is dropped or run again. It signals the group only when `ps` still shows the mark on that pid, so a reused pid is never signalled; a leader already gone can't be confirmed and its group is left alone. The login is never written anywhere by berth; a script that prints it is the script's business, and the log lives with the rest of the state.

## Options considered
- Filtering seed files: an allowlist of statements, refusing any name equal to another database, policing `sql_mode` and character sets, unwrapping versioned comments and checking tables after they are created. Tried and rejected: a seed file is the user's own SQL, as trusted as the `command` script that sits next to it in the config, which no filter can cover. The filter refused real files, such as one with a table named like a database on the server or a dump with stored routines, and over a thousand lines of it bought no protection from a user who can run anything with that login anyway.
- Sending the file to a `mysql` client: needs a client installed and matching the server (0043).
- Stripping `DEFINER` from a dump's views and triggers: statements run as written; a dump whose definer is another user needs the same privilege it would with the client.
- Validating the whole file before running any of it: reads it twice, for a partial load that is already safe because the target is berth's own and reads `failed`.
- Running the script with no shell, or with its arguments split by berth: a shell is what `post-add` uses, and users write the same kind of one-liner.
- Identifying a script by its start time from `ps -o lstart=`: `ps` takes tens of milliseconds, and the run must be recorded before it can begin; the mark is known before the process starts. Withholding the clone process's pid from `status` until the script had run for a moment: nothing reads that pid in production, and it only hid the orphan.
- A dedicated log only on failure: a script's output is useful when it succeeds too, and there's only one place to look.

## Evidence
`e2e/host_seed_test.go`, `e2e/host_command_test.go` and `e2e/host_command_recovery_test.go` run against a MySQL 8.4 server in Docker. They cover a seed from `mysqldump` loading with its trigger, a file read from the main worktree, a file that mentions main in text still loading, a gzipped file loading the same as the plain one, a missing or broken file failing its own database while the others finish, progress and recovery after a kill, the command's documented variables, the command running once across repeated `add`s, its exit status deciding ready or failed, its log named by `status` even after a kill, the password kept out of berth's output, a killed command's script being gone before `status` reads failed and before it runs again, and the reported size of a seed, a command and a dump. `internal/volume/script_unix_test.go` checks that a recorded run is stopped and a process without its mark is left alone. `internal/mysql/seed_test.go` covers the scanner: escaped and doubled quotes, `NO_BACKSLASH_ESCAPES`, `DELIMITER`, versioned comments passed through, a truncated string, the 64 MiB bound and a byte order mark. A spike ran a 5.8 MB dump from `mysqldump` 9.3 of a database with a trigger and a view, taken from an 8.4 server, through `berth add --wait`: tables, checksums, the trigger and the view all matched.

## Undoing it
The scanner and loader are `internal/mysql/seed.go`; the clone-process side is `internal/cli/seeds.go`; the config shape is `Database` and `validateDatabaseEntry` in `internal/config/config.go`. Removing the two strategies leaves `file` and `command` entries in berths' records, which older code refuses as unknown strategies; drop them from the config first.
