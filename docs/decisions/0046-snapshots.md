# 0046. Snapshots

Status: accepted

## Context
`berth snapshot` in the main worktree takes a consistent copy of every database configured as `snapshot` and keeps it outside the worktree, per repository, until the next `berth snapshot`; `add` and `reset` then clone from it, so main never pauses for them, and `berth status` says how old it is (design, Commands, Per-database control). A snapshot holds the user's data and is taken by berth on its own, so the rules for a copy of main (0043) hold: nothing of main's pauses without saying so first, and nothing in the result points back at another database. A `kill -9` must leave the previous snapshot usable, and `remove` must never delete one. This record covers where snapshots live, their format and how one replaces another.

## Decision
- **Where:** `<state>/snapshots/<hash>/`, where `<hash>` is 16 hex characters of the SHA-256 of the repository's main worktree path. Berth's state directory is already per user and outside every worktree, and a hash keeps repositories that share a state directory apart without ever putting a path in a file name. A moved repository starts with no snapshot; `berth snapshot` makes one, and `add` and `reset` follow the move because `registry.Find` refreshes the record's repository from git.
- **Layout:** a `manifest.json` naming the current generation, and one directory per generation, `gen-<random>`, holding one gzipped stream per database, `001.gz` and on. The directory is `0700` and every file `0600`, since snapshots hold the user's data. The manifest names the server's host and port, the generation, and for each database its key, source, `file`, character set, collation, size, `file_bytes`, `source_missing`, the time its read began and the notes it left, and nothing else: never a user or password, in the manifest or anywhere under the directory.
- **Atomic replacement:** a new snapshot is written complete into a fresh generation directory. Only when every database in it is finished does berth write the manifest to a temporary file, flush it and `rename` it over `manifest.json`, the one step that changes what is current. Whatever stops the run before that rename, `kill -9` included, leaves the previous manifest and generation untouched. The next `berth snapshot` removes every generation directory the manifest doesn't name before starting, so a partial one is gone without anyone cleaning up. After the rename the old generation is removed too. A set of databases is one generation: if any one fails, none replace the previous snapshot, and `berth snapshot` exits `4`. So does a database main no longer has when the current snapshot holds data for it, since an empty entry would replace that data. A failure to remove the replaced generation after the rename only warns: the new snapshot is current, and the next `berth snapshot` removes the leftover.
- **Concurrency:** `berth snapshot` holds the main worktree's lock (`registry.LockWorktree`) for the whole run, so a second run waits rather than interleaving. A clone run reads the manifest once and opens the files of every database it will restore before it starts, without that lock, so one run uses one generation throughout, and the open descriptors keep a replaced generation's data readable until the run ends. If `berth snapshot` removes that generation between reading the manifest and opening a file, it reads the manifest again, so a run never stops on a swap it raced with. A run holds one descriptor per database it restores, well within what Go raises the file limit to.
- **Format:** each database's stream is a sequence of frames, a kind byte and three length-prefixed fields: table (name, `CREATE TABLE`), rows (the statement), view (name, `CREATE VIEW`) and trigger (name, `sql_mode`, `CREATE TRIGGER`). A snapshot is a structured stream rather than a plain SQL file, so nothing has to parse it to apply the same guards as a copy. A `format` number in the manifest lets a later version refuse an old layout, reading as no snapshot, rather than misreading it.
- **Taking one:** `Snapshot` in `internal/mysql` runs the read side of `Copy` unchanged: one `START TRANSACTION WITH CONSISTENT SNAPSHOT`, the same `LOCK TABLES` on non-InnoDB tables with the same announcing rule (a table that would newly need holding fails that database rather than pausing unannounced, and `berth snapshot` says to run it again), the same `FLOAT` and hex encoding of row values and the same statement sizes, written to the frame stream instead of to a target database. `Copy` and `Snapshot` share one `consistentRead` with the destination behind an interface (0043's write side becomes `databaseSink`; a snapshot is `snapshotSink`).
- **Guards:** everything a copy keeps out stays out of a snapshot and is reported, by `berth snapshot` and by the berth's `notes` on restore: a table whose engine keeps its rows elsewhere, one whose definition places rows or files outside the database, a foreign key into another database, a view or trigger that names another database or can't be read through, and a table left out because its definition says so. At restore the same checks run against the created table and the server as it is then, since the swap of an engine and a database named in a trigger can only be judged there, with what the snapshot holds of a table left out skipped. No new SQL-text filter was added beyond those.
- **Restoring:** a `snapshot` database is a `databases` entry in the clone state like `dump`, `file` and `command` (0043, 0045), through `clonedStrategy`, so `add`, `add --wait`, `status --wait`, `reset`, progress, recovery from `kill -9` and the ownership check before anything is dropped are all the existing path. It reads no table of main's: `add` with main's tables locked finishes. In `add`, a database with no snapshot, or one taken from another server or under another source name, fails with a message naming `berth snapshot`. `reset` clones from the snapshot again.
- **reset refuses first:** `reset` makes the same checks before anything is dropped, in `planDatabaseReset` beside its other refusals and in its dry run too: every `snapshot` database must have its key, source and server in the snapshot, and every seed database's file must open. It exits `1` having dropped nothing, since a dropped berth with no way to be rebuilt is worse than a refusal.
- **Age:** when a restore finds its snapshot it records the time the snapshot's read began on the clone entry, and `status` reports the age from that, as a line in the table and `snapshot_taken_at` and `snapshot_age_seconds` in JSON, so a later `berth snapshot` doesn't change what a berth says about its own data until the berth is reset.

## Options considered
- A staging database on the server, copied into place: needs no format of its own, but `RENAME DATABASE` doesn't exist (0043), it would add a database main's server didn't have, and it couldn't be replaced atomically.
- A plain SQL text file, reused through the seed loader (0045): the load path exists, but a seed is the user's trusted code and is deliberately not guarded. A snapshot taken by berth has to apply the copy's guards at restore, against the created table, which SQL text can't support without filtering it, and the seed loader's scanner adds a second reading of what the stream already has as whole statements.
- One file per table: more files for a format that is only ever read start to end, with nothing gained.
- Keeping a snapshot beside each berth: a snapshot is the source's, shared by all berths of a repository, and the design says it outlives them.
- A symlink flipped by `rename`: as atomic as the manifest, and it needs the same directory for the generation; a file also carries the metadata a symlink can't.
- Replacing one database at a time: a kill between two would leave a mix of two snapshots, and a set of databases is taken for one point of intent.
- Sequencing on the same lock for restores: a restore would then wait for a long `berth snapshot` that has nothing to do with the previous, still valid, snapshot it can use.

## Evidence
`e2e/host_snapshot_test.go` covers a berth holding main's data as of the snapshot and not of `add`, changes to main reaching the berth only after the next snapshot and `reset`, the age in `status`, `add` failing a database with no snapshot and naming `berth snapshot`, the dry run, a killed snapshot leaving the previous one usable and the next one recovering, `remove` and `prune` keeping the snapshot, snapshots kept per repository, nothing added to the main worktree, a snapshot under write load holding whole transactions while main keeps writing, and `add` from a snapshot finishing while main's tables are locked. Unit tests in `internal/snapshot` cover file modes, the previous snapshot reading until the new one is committed, cleanup of a killed run's generation, and a manifest of another format reading as no snapshot. The frame round trip and a truncated stream are tested in `internal/mysql`.

## Undoing it
Storage and atomic replacement are `internal/snapshot`; the stream, `Snapshot` and `Restore` are `internal/mysql/snapshot.go`; the command, restore step and status age are `internal/cli/snapshots.go`, `dumps.go`, `volumes.go` and `berths.go`. Reverting leaves `<state>/snapshots/` behind, which older code ignores; delete it by hand. Records with `snapshot` databases are refused as an unknown strategy by older code, so change those first.
