# 0048. Windows

Status: accepted

## Context
The design says berth runs natively on Windows 10 and later, that `post-add`, `pre-remove`, `command` and the git hook run with the `sh` Git for Windows installs, found through git's own install, failing with a message naming it when there is none, that the registry lives under `%LOCALAPPDATA%\berth`, and that the managed block joins `COMPOSE_FILE` with `;` (design, Platforms). Every guarantee holds on every platform berth supports. Until now the Windows build compiled with its locks, the background clone process, free space, stopping a clone and stopping a `command` script all returning "not supported", and it ran scripts with whatever `sh` was on PATH. Several mechanisms the Unix build relies on have no Windows counterpart: `flock`, a descriptor passed to a child past the standard three, process groups and sessions, `statfs`, `ps` and `lsof`, and a rename over a file another process has open. Copy-on-write and symlinks on Windows are in [0049](0049-windows-files.md).

## Decision
On Windows berth locks with `LockFileEx`, hands a lock from the process that schedules work to the one that does it through a two-byte lock and a named event, ends a clone process's children with a job object that kills them when the clone process ends, runs scripts with Git for Windows' `sh.exe`, and reads ports, processes and free space through the Windows API. CI runs `go vet`, the unit tests and the whole e2e suite on `windows-2025`, with Linux containers from Docker Engine inside WSL2.

### Details
- **Locks.** The registry lock, a worktree's lock and SQLite's locks are byte-range locks taken with `LockFileEx`, which Windows releases when the handle closes or the process ends, `taskkill /F` included, as the kernel releases a `flock`. The registry and worktree locks hold one byte of their lock file, far past its end, since Windows locks are mandatory and a lock on bytes someone reads, even the start of an empty file, fails that read. Lock files open with `FILE_SHARE_DELETE`, because `remove` deletes a berth's lock files while holding them, as it can on Unix. SQLite's are the ranges its win32 VFS uses (`os_win.c`): the PENDING byte held exclusively while the 510-byte SHARED range is taken shared, and the first two reader slots of the `-shm` file, at the same offsets as on Unix. Windows locks are mandatory, so a byte copy can't read the PENDING and RESERVED bytes of a database over 1 GiB while main's writer holds them; [0049](0049-windows-files.md) records how the copy reads around them.
- **Passing a lock.** On Unix `add` passes the clone lock, and the post-add lock, to the process it starts as fd 3, so the lock is held from before the state reads `cloning` until that process ends. A Windows lock belongs to the process that took it and can't be passed, and Go can't pass a descriptor past the standard three there either. So a passable lock is two bytes of the lock file, past its end as above, and holding it means holding either byte: taking it (`TryLock`, `WaitUnlocked`) takes the first then the second, and fails or waits when either is held. `add` holds both, lets go of the second, and starts the child with the lock's path and the name of a fresh event in `BERTH_LOCK_HANDOFF`. The child takes the second, the only byte anyone takes without holding the first, sets the event, and `add` waits on the event and the child's process handle together before letting go of the first. At no moment is neither byte held. A child that ends first fails the start, as a failed `exec` does on Unix. A child whose event is gone, because `add` died before it got there, does nothing, since the lock may have been recovered meanwhile.
- **Ending what a clone started.** The clone process puts itself in a job object it alone holds a handle to, with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Everything it starts joins the job: `docker` commands, and a `command` script with every process the script starts. When the clone process ends, however it ends, Windows closes the handle and ends the whole job. `remove` stops a running clone by ending the clone process, which ends the job, where Unix kills the process group. Recovery still stops the script the clone entry records, as on Unix, but by its pid and the mark in its command line, read with `NtQueryInformationProcess`, ending it and waiting for it to go. A script on Windows gets no `SIGTERM` first: Windows has no signal a process without a console can catch.
- **Which process is the clone.** `remove` finds the clone process by the pid `add` wrote to `<state>/<id>.pid`, and it gets there whenever the clone lock is held, which `status`, `--wait` and a waiting `post-add` do for a moment too. The file outlives the process, and Windows gives a dead process's pid to the next process soon after, so ending that pid unchecked could end the user's editor. So `remove` opens the process, ends it only when its image is berth's own executable, compared as a file, and its command line ends with `__clone <id>`, and ends it through the handle it checked, which keeps the pid from changing hands in between. Unix now checks too, though the risk there is smaller since a pid comes round again only after the kernel has used every other one and the kill reaches only a process leading a group: `ps` must show the pid's command line ending with `__clone <id>` before berth kills the group. With no `ps`, berth kills nothing and `remove` waits up to 30 s for the clone to end, then says to run it again.
- **The `command` gate.** The outer shell reads the gate from its stdin rather than fd 3, and points stdin at `/dev/null` before running the script, so the script never holds the gate.
- **Detaching.** A clone or post-add process starts with `CREATE_NO_WINDOW`, a console of its own with no window, so it outlives the terminal or hook that ran `add`, and nothing it starts opens a window.
- **Scripts.** The script and its arguments from `$1` on reach `sh` through the environment, in variables the shell takes out again before the script runs, not on the command line: a program built for Git for Windows' `sh` parses its own command line, dropping quotes, expanding braces and wildcards, and collapsing doubled backslashes, so `sh -c '<script>'` from Windows wouldn't run the script the user wrote, and `config edit` would open `C:\Users\OBrien` for a worktree under `C:\Users\O'Brien`. `$0` stays on the command line, since only `sh -c` sets it: berth puts there only the name `sh` reports errors under, or a `command` script's mark, which recovery reads from the command line. To find `sh`, berth runs `git --exec-path` and looks for `bin\sh.exe`, then `usr\bin\sh.exe`, in that directory and up to three above it, which finds Git for Windows, its portable build and an MSYS2 git; then in the directory of `git.exe` and the one above. `bin\sh.exe` comes first because it puts git's own tools on PATH before starting the `sh` in `usr\bin`, as git does for its hooks. With no git, or a git with no `sh.exe` such as MinGit, the script fails with a message naming `sh.exe` and Git for Windows: `post-add` reads `failed`, `pre-remove` stops `remove` before anything is removed, and the database reads `failed`. `config edit` runs `%VISUAL%` or `%EDITOR%` through the same `sh`. Git runs the post-checkout hook with its own `sh`, and when it can't find one it prints only "cannot spawn" and the hook's path, which berth can't change, so `hook install` refuses, naming `sh`, before writing anything. The other options were `doctor` naming the missing `sh`, which only helps someone who runs it, and a native `post-checkout.exe`, which would no longer run through `sh`.
- **Ports.** A bind refused with `WSAEADDRINUSE` or `WSAEACCES` means the port is in use, as `EADDRINUSE` and `EACCES` do on Unix.
- **Processes.** `doctor`'s listener check lists the processes listening on a port with `GetExtendedTcpTable`, names each by its image with `QueryFullProcessImageName`, and reads its current directory from its process parameters, where Unix asks `lsof`. A listener `wslrelay` is a port published by a Docker engine in WSL.
- **Free disk.** `GetDiskFreeSpaceEx`.
- **Replacing state files.** Berth writes state to a temporary file and renames it over the old one. Windows refuses that rename while any process has the old file open, as any berth command reading state has for a moment, so on Windows the rename is tried again for up to 2 s.
- **Snapshots.** A snapshot file is opened with `FILE_SHARE_DELETE`, so a newer snapshot can replace the generation a reader still has open, as on Unix. The snapshot directory gets an access control list granting the user alone access, inherited by everything in it, where Unix makes it `0700`.
- **Where state lives.** `XDG_STATE_HOME`, when set to an absolute path, wins over `%LOCALAPPDATA%`, since a user who sets it on Windows means it; otherwise the design's `%LOCALAPPDATA%\berth`.
- **Paths berth names.** `[state.sqlite] files` keep the config's forward slashes in berth's output on Windows, so berth names a file as the config does, and `doctor` searches cloned files for the source path in either slash, since tools on Windows write both.
- **A detached process's directory.** A clone or post-add process runs in berth's state directory, not the worktree `add` ran in, since Windows refuses to remove or move a directory a running process has as its current directory.
- **The SessionStart hook's watchdog.** It gives `berth status` 0.7 s on every platform, where [0038](0038-claude-code-session-start-hook.md) records 0.8 s, and reads the session JSON with one process rather than two: starting a process under Git for Windows' `sh` is slow enough that the script's own part of the 1 s budget came to a quarter of a second, and a busy berth took the hook to 1.05 s. Even then it took 1.17 s and 1.43 s on a loaded CI runner, so the budget is 2 s on Windows and stays 1 s on macOS and Linux. Counting the 0.7 s from the start of the script would have held 1 s more often, but it leaves berth about 0.3 s on Windows, enough to report a healthy berth as busy.
- **Line endings.** `.gitattributes` checks every text file out with LF, so a Windows checkout embeds the agent guides as they are written.
- **CI.** The `windows` job in `.github/workflows/test.yml` runs on each pull request. The runner's own Docker Engine runs Windows containers only, so the job installs Docker Engine in a WSL2 distribution and runs `dockerd` from the same WSL session that runs the tests, since the engine stops with the session that started it. The tests run on the Windows side with `DOCKER_HOST` at the WSL VM's own address: through WSL's localhost forwarding the Windows client gets none of a container's output from `docker run` or `docker exec`, while ports containers publish answer at 127.0.0.1 as on any machine. The job also installs a MinGit with its `sh.exe` removed, for the tests of a git with no `sh`. Every download is pinned by version and SHA-256. The tests' temporary directory is on the runner's D: drive, excluded from Defender, since `berth add` copying a 310 MB tree took 38 s on C: and under 10 s there.

## Options considered
- Passing the lock as an inherited handle, through `SysProcAttr.AdditionalInheritedHandles`: the handle arrives, but a Windows lock belongs to the process that took it and doesn't go with the handle, so the lock would go when `add` exits.
- Letting the child take the lock itself after `add` lets go: between the two, `status` would take the free lock and call the clone failed, the gap 0021 closed on Unix.
- A second lock file guarding the hand-off, which every reader checks: the same protection, with two files to reason about and a lock order to keep, where two bytes of one file need neither.
- A named mutex: Windows abandons it when its owner dies, but it can't change hands between processes either, and berth's Unix code is built around a lock file that can be tried and waited on.
- Killing a clone's children by walking the process tree from its pid: the tree goes stale as soon as a parent exits, a pid can be reused, and a process killed with `taskkill /F` runs no code to do the walking. The job object needs no code to run at the moment of death.
- A job object created by `add` and assigned to the clone process: `add` would have to keep the only handle, and the job would end when `add` does.
- Running scripts with the `sh` on PATH: Windows has none by default, and a PATH that happens to hold WSL's `bash.exe` or another one would run scripts in a different world.
- `usr\bin\sh.exe` before `bin\sh.exe`: it starts without git's tools on PATH unless the user's PATH has them.
- Docker Desktop on the runner: not part of the runner image, and Docker Engine in WSL2 already runs the Linux containers the tests need.
- WSL's mirrored networking, so that `127.0.0.1` reaches the engine directly: in a probe run the distribution then resolved no host names, so Docker Engine couldn't be installed.
- `DOCKER_HOST=tcp://127.0.0.1:2375` through WSL's localhost forwarding, as the spike did: `docker run` and `docker exec` exit, but print nothing of the container's output, so every test reading a container's output, and the clone's own copy stream, failed.
- Running the e2e tests inside WSL against a Linux build: that tests the Linux build, not the Windows one.
- Opening every state file with `FILE_SHARE_DELETE` instead of retrying the rename: every reader in berth would have to open files differently, where the retry is in one place.

## Evidence
Spike runs on GitHub's `windows-2025` runner: the runner's own Docker Engine reports OSType `windows` and `docker run alpine` fails with "no matching manifest"; Docker Engine installed in WSL2 and run with `-H tcp://0.0.0.0:2375` is reached by the Windows client, reports OSType `linux` and runs containers, and a port published with `-p 18080:80` answers at 127.0.0.1 on Windows. A separate step, or `Start-Process`, did not keep the engine alive past its WSL session. A bind mount of a Windows path, `-v C:\spike:/m`, fails with "invalid mode", since a plain engine doesn't translate Windows paths as Docker Desktop does; named volumes work, and the fixtures use named volumes only, so no test is skipped for it. A probe on the same runner found that through localhost forwarding `docker run alpine echo` and `docker exec` print nothing on the Windows side, while through the VM's address they print as expected; that a server published on 127.0.0.1 or 0.0.0.0 in WSL answers at 127.0.0.1 on Windows, sending first as MySQL does; and that WSL's relay holds such a port on Windows' 127.0.0.1, so binding 127.0.0.1 there fails while binding 0.0.0.0 succeeds, which is why berth's port check tries each address on its own.

The acceptance tests in `e2e/windows_groundwork_test.go` run in the `windows` job: two `add` at once give one berth; `list` and `status` return within 5 s while another `add` copies; a clone killed with `taskkill /F` mid-copy reads failed and `add --wait` recovers a copy identical to main's; a `command` script and both of its child processes are gone within 10 s after its clone process is killed with `taskkill /F`, and after `remove`; a port held on 0.0.0.0 is never assigned; `post-add`, `pre-remove` and `command` run a script only a POSIX shell can run; with MinGit and no `sh.exe`, each fails naming `sh`, and `pre-remove` keeps the berth; the registry lives under `%LOCALAPPDATA%\berth`; and `COMPOSE_FILE` splits on `;`. The rest of the unit and e2e suites run there too. Unit tests: `internal/shell` finds Git for Windows' and MSYS2's `sh` and looks no higher than the install; `internal/volume` stops a recorded script on Windows by the mark in its command line and leaves a process without it; `internal/cli` ends a clone process, and leaves one running another berth's clone or another executable; `internal/safefile` replaces a file once its reader closes it; `internal/snapshot` checks the snapshot directory's access control list.

Tests that can't set up their premise on Windows skip on an explicit check of that premise, never on the platform's name: the image comparison's permission case when a `chmod` leaves the mode as it was, the hook's executable bit when the filesystem keeps none, and signal forwarding to `berth exec` when the platform can't send a process `SIGINT` or `SIGTERM`. Tests that write a script to stand in for `git`, `docker` or `berth` on PATH put a small program beside it on Windows, built from `e2e/testdata/shim`, that runs the script with Git for Windows' `sh`, with that `sh`'s argument globbing and POSIX path conversion turned off so the script's arguments reach the real program unchanged.

Windows-only harness code doesn't change what a test asserts: it runs the same scripts through Git for Windows' `sh`, spells paths the way that `sh` and the JSON output do, ends the processes a test leaves running in its directory before Windows has to delete their open files, picks another port when one free on Windows is taken inside WSL's VM, and on Windows checks a directory's access control list where Unix checks its mode.

## Undoing it
The Windows code is in files ending `_windows.go`, with the system calls in `internal/winsys`; deleting them brings back the "not supported" stubs in the `_other.go` files once their build constraints drop `windows`. The `sh` lookup is `internal/shell`, and on Unix it returns `sh` as before. `internal/safefile` is `os.Rename` and `internal/lockfile` is `os.OpenFile` outside Windows. The CI job is one job in `.github/workflows/test.yml`.
