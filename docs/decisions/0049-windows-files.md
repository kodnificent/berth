# 0049. Windows files

Status: accepted

## Context
The design says cloned files on Windows are block clones on ReFS, the filesystem of a Dev Drive, and full copies on NTFS, which `add` and `doctor` report naming Dev Drive; that symlinks into main point into the berth, junctions are cloned as junctions, and a path berth can't make a symlink in fails naming Developer Mode while the other paths finish (design, Platforms, `cow`, "Nothing points back at the source"). Windows has no `reflink` or `clonefile`, a symlink is fixed as a file or a directory when it is made, Windows byte-range locks are mandatory so reading what a writer has locked fails, and `doctor` must find main's path under backslashes and a drive letter tools lower-case. This record covers how those are met.

## Decision
- **Block cloning.** Berth uses `FSCTL_DUPLICATE_EXTENTS_TO_FILE`, one file at a time as on btrfs and XFS: `cowTree` stays "unsupported" and `copyFile` calls `reflink`, which is `winsys.BlockClone`. There is no whole-tree call on Windows.
- **The steps of a clone** (`internal/winsys/clone_windows.go`): read the source's integrity settings and cluster size with `FSCTL_GET_INTEGRITY_INFORMATION`, which fails outright on NTFS and so doubles as the check that the filesystem can block clone; give the destination the same integrity settings, since ReFS refuses a clone between files with different ones; mark the destination sparse while it is empty so extending it allocates nothing, and a 2 GiB clone doesn't need 2 GiB free; set its length to the source's; duplicate the extents in regions of at most 1 GiB (a single call takes under 4 GiB, and 1 GiB divides evenly by any cluster size); clear the sparse attribute again unless the source is sparse.
- **Cluster alignment.** A region must start and end on a cluster boundary, 4 KiB or 64 KiB. Berth clones from offset 0 to the end of the file, so the end is rounded up to the next cluster: ReFS accepts a region past the end of the file and the file keeps the length it was set to. An empty file needs no region, and counts as cloned.
- **Fallback and how it is reported.** Any failure at any step, including `ERROR_NOT_SAME_DEVICE` for two volumes and whatever a filesystem without block cloning returns, makes `reflink` fail and `copyFile` copy the bytes. A failure after the destination was extended first empties it and clears sparse, so the byte copy starts clean. `add` counts files shared and copied and reports `cow`, `copy`, or `cow, with N files copied in full`, as on Linux; on NTFS a full copy is followed by one line naming Dev Drive, and `doctor`'s platform check, which already tries a real clone from main into the worktree, adds the same hint.
- **Symlinks.** A link is copied with the file-or-directory kind of the source link, read from the source's attributes, rather than the kind `os.Symlink` would guess by looking at what exists at the target at the moment it is made, since a link can sort before what it points at. `Repoint` keeps the kind too when it rewrites a link into the berth. Berth asks Windows to allow an unprivileged link (`SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE`), which succeeds under Developer Mode, and otherwise needs the privilege an administrator holds; builds of Windows before 14972 reject that flag, so a refused call is retried without it, as `os.Symlink` does. `ERROR_PRIVILEGE_NOT_HELD` becomes `clone.ErrNoSymlinkPrivilege`, which names Developer Mode.
- **A path refused a symlink.** That error alone doesn't abort `materialize`, wherever the path came from: `.env` files, `[files] clone`, and the gitignored compose files berth copies. The other paths, the override and the managed block are written and the excludes added, and `add` then ends with one error naming every refused path, exit `1`, before it copies SQLite or starts anything. A path `Tree` made is removed, so it fails as one. A merge into a directory the berth already had keeps what it copied, recorded in `Result.Created`, and the path isn't recorded as cloned, so `add` after Developer Mode is on fills in the rest. Every other clone error still stops `add` at once, as it does on every platform.
- **No link into main survives a failure.** `Repoint` runs only after a whole copy, so a copy that fails part way holds links still aimed at main. `Tree` removes what it made on any failure, and `merge` removes a tree `Repoint` failed on. A process killed between the two leaves the same state where no code runs, so `merge` also rewrites a link the berth already has when main's has one at that path: only an absolute target leading into main, since a relative link may be one git checked out, and never one already leading into the berth, which is also "under main" when the worktree sits inside main's directory.
- **Junctions.** A junction is a directory reparse point holding an absolute target, and needs no privilege to make. Go reports one as `ModeIrregular`, not `ModeSymlink`, so `copyTree` used to drop it. Copied by reading the target with `os.Readlink` and making a new junction with `FSCTL_SET_REPARSE_POINT` and a mount-point reparse buffer, then `Repoint` retargets it into the berth like a symlink. A volume mount point has the same tag but a target naming a volume; it isn't a junction a berth could hold and is left out as before.
- **Removing.** Go 1.23 and later never follow a junction: `os.Remove` and `os.RemoveAll` delete the junction, not its target. `removeUntracked`'s branch for a directory holding tracked files read the directory before removing its children, which would follow a link or junction recorded as berth's own, so it now removes one of those directly, never reading through it. A parent can become a link too, when a branch tracks a symlink where main has a directory, and then `os.RemoveAll` on a recorded path goes through it into main. `planTeardown` applies `realDirs`, the check SQLite's copies already used, to every recorded file: one whose parent is no longer a real directory is left, and `remove` and `prune` say so on stderr. That covers macOS and Linux too, where the same branch does the same damage. `realDirs` refuses a junction as it does a symlink, and says so.
- **Seeing a link's real target.** A link can reach main through an alias, and comparing paths as text would call that outside main. `Retarget` compares both the target and main's root as Windows resolves them, through `GetFinalPathNameByHandle` on Windows, since `filepath.EvalSymlinks` gives up at a junction with more of the path after it. A relative link is checked the same way, so one climbing out of main through an alias lands in the berth rather than being pinned to main. A rooted target with no volume, `\\repo\\x`, isn't absolute to `filepath.IsAbs` on Windows, so it is given its link's volume first.
- **SQLite's locks.** Windows byte-range locks are mandatory, so a read of bytes another handle holds exclusively fails, and past 1 GiB SQLite's lock bytes are inside the file: `PENDING` and `RESERVED`, 0x40000000 and the byte after, which a writer holds while it fills its journal and waits for readers. The copy holds `SHARED` on the 510-byte range after them, which keeps any writer from getting exclusive on that range, so those two bytes are the only ones a byte copy can be refused. They sit on SQLite's lock-byte page, which SQLite sets aside and never reads or writes, so the byte copy reads around them and writes zeros in their place. A block clone needs no such care: `FSCTL_DUPLICATE_EXTENTS_TO_FILE` was not refused across a byte another handle held exclusively (see Evidence), so a large database under a writer still clones on a Dev Drive, and were it ever refused the byte copy above takes over. A sidecar's bytes at that offset are its own data, so only the database file reads around them.
- **Doctor's source path.** On Windows the check folds ASCII case on both the file and the source path, so `c:\repo` finds `C:\repo`; byte offsets stay put so line numbers are unchanged. Elsewhere case stays significant.
- **CI.** The `windows` job makes a real Dev Drive and sets `BERTH_TEST_DEV_DRIVE` to a directory on it. `diskpart` makes and attaches a 64 GiB expandable VHD, since a Dev Drive must be at least 50 GB and the runner has no Hyper-V module for `New-VHD`, then `Format-Volume -DriveLetter R -DevDrive` formats it, and the job fails unless `fsutil devdrv query R:` says it is a developer volume.

## Options considered
- `CopyFile2`, which block clones on recent Windows releases: it doesn't say whether it cloned or copied, so `add` couldn't report the path that ran.
- A hard link: shares data, but writes in the berth reach main, the very thing a clone must never do.
- A plain ReFS clone with no sparse step: it needs free space equal to the file's full size even though nothing new gets stored, which is a clone refused on a nearly full Dev Drive.
- `FSCTL_DUPLICATE_EXTENTS_TO_FILE_EX` for atomic range semantics: unneeded with the destination private to berth until it is finished.
- For SQLite past 1 GiB on ReFS, cloning around the cluster holding the lock bytes: it assumes a clone across a locked byte would be refused. A probe on the runner showed it isn't, and a refusal would land on the byte copy anyway, so the extra code bought nothing.
- Failing a path on any clone error instead of only a refused symlink: a disk-full or permission failure would then carry on past other paths, a behaviour change on every platform that nothing here asks for.
- Leaving a partial clone in place for a retry to fill in, where `Tree` made the path: it would hold links still aimed at main and nothing records it, so `remove` couldn't find it. A merge into a directory the berth already had does keep what it copied, since those files are recorded and can stay.
- Repointing every link on every `add` instead of only an absolute link into main: it would pin a relative link git checked out, which the berth's own branch owns.
- Refusing the removal with an error when a recorded parent became a link: `remove` would then fail, and keep the record, over a path the branch changed on purpose.
- A plain ReFS volume in CI instead of a real Dev Drive: it gives block cloning alike, but the tests' names would claim something the job didn't do.

## Evidence
A probe on GitHub's `windows-2025` runner, on a VHD-backed ReFS volume with 4 KiB clusters, measured what the tests assume: `FSCTL_GET_RETRIEVAL_POINTERS` gives two separately written files on ReFS different clusters (32784, 32900 and 32785, 33155) and a block clone the same ones as its source (32784, 32900), so the cluster check can tell a clone from a copy; a process with `SeCreateSymbolicLinkPrivilege` deleted through `CreateRestrictedToken` and started with `CreateProcessAsUser` could still make a symlink while `AllowDevelopmentWithoutDevLicense` read 1 and could not once it was set to 0, with no reboot; and a block clone of a 1 GiB and larger file across a byte another handle held exclusively returned no error. That volume was plain ReFS, not a Dev Drive. The `windows` job now makes a real Dev Drive, and this record holds no measurement from one.

What the tests prove: `e2e/windows_files_test.go` covers block clones on a Dev Drive, full copies on NTFS with the Dev Drive hint, symlinks and junctions pointing into the berth, and a path refused a symlink, and `e2e/windows_files_more_test.go` adds a file ending part way through a cluster cloning byte for byte and sharing clusters, an empty file counting as cloned, a path refused a symlink leaving nothing behind and being finished by a later `add`, a junction removed without touching its target, and a write into the middle of a block-cloned file leaving main's copy unchanged. Rewriting a whole file frees the clone's clusters, so only that last test writes onto clusters still shared. `internal/sqlite` checks a copy past 1 GiB while another handle holds `RESERVED`, as a byte copy and as a block clone that must not fall back; `internal/clone` checks that a directory link whose target sorts after it keeps its kind. Microsoft documents the rules a clone must meet in "Block cloning on ReFS" and the `FSCTL_DUPLICATE_EXTENTS_TO_FILE` reference: same volume, same integrity settings, cluster-aligned regions and under 4 GiB a call.

## Undoing it
The block clone, junction and final-path system calls are `internal/winsys/clone_windows.go`, used by `internal/clone/cow_windows.go`, `internal/clone/links_windows.go` and `internal/sqlite/cow_windows.go`. To go back to full copies, delete those four files, `internal/clone/links_windows_test.go` and `internal/sqlite/lock_bytes_windows_test.go`, drop `!windows` from the build constraints of `internal/clone/cow_other.go` and `internal/sqlite/cow_other.go`, and remove the constraint from `internal/clone/links_other.go`. The carry-on past a refused symlink is `refusals` in `internal/cli/files.go`; deleting its `add` calls makes that error stop `add` like any other. Rewriting an existing link is the `isLink` branch in `merge`, and removing what a failed copy made is the `err != nil` cleanup in `Tree`. The parent check on removal is the `realDirs` call in `planTeardown`. The Dev Drive is one step in `.github/workflows/test.yml`.
