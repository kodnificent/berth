# 0050. Postgres template copies

Status: accepted

## Context
`template` gives a berth a copy of main's Postgres database made by the server itself (design, Host Postgres). It runs in the background as `dump` does, with progress, `add --wait`, `status --wait`, recovery after `kill -9` and `reset` (0043, 0045, 0036). Postgres copies a database only while no other session is on it and holds new connections to it back until the copy ends, so a session on main's database fails that database, naming the session's application and client address, unless `disconnect = true` lets berth end those sessions, saying so first; the pause on new connections is announced before the copy. The copy is instant where the server's data directory has copy-on-write, and `add` says which path ran. The login is not a superuser: it has `CREATEDB` and owns main's databases. Built on the engine seam (0047).

## Decision
- **Same path as `dump`:** `template` is one more strategy in `clonedStrategy`, so it is a `databases` entry in the clone state, run by `berth __clone` under the clone lock, recovered, waited on and reset exactly as a dump is. The record names the target before it exists (0040), and the clone process drops and makes only a target the record owns.
- **Announcing:** `add` and `reset` print, for each template entry, that new connections to main's database will pause for the copy, and with `disconnect` that berth will end the other sessions on it, before the clone process starts. Whether to end sessions is saved on the entry as `disconnect` when announced, and the clone process ends sessions only for an entry that carries it, so a config changed after `add` can't end sessions nobody was told about.
- **The copy:** one connection to the maintenance database runs `CREATE DATABASE "<target>" TEMPLATE "<source>"`, with `STRATEGY FILE_COPY` on 15 and later (13 and 14 have no clause and copy files anyway), `statement_timeout = 0` for the session, and on 14 and later `client_connection_check_interval = '1s'`, so the server abandons a copy whose client died instead of finishing it with main's new connections held back. The target is created owned by the login, so `Drop` works on it.
- **Sessions:** before the copy berth lists `pg_stat_activity` on the source, leaving out itself and autovacuum (which `CREATE DATABASE` stops on its own). A login that is not a superuser sees an autovacuum worker with no role and no `backend_type`, so every row with no role is left out as autovacuum: every other process that can be on a database runs under one. Without `disconnect`, any session fails that database with a message naming each one's `application_name` and client address (or "a local socket"), and nothing is ended. A session under another role shows its application and role but not its address, so berth says the address can't be seen rather than guessing. With `disconnect`, berth works out from `pg_has_role` and `rolsuper` which sessions the login may end, the rule `pg_terminate_backend` applies; if any may not be ended, it fails that database naming them and ends none, else it ends exactly the listed pids on the source database and starts the copy, trying up to three times when sessions reconnect in between. The login's own role is never named, since it is the user berth connects as.
- **Which path ran:** on 18, `file_copy_method` is a user setting (`pg_settings.context = 'user'`, values `copy` and `clone`), so berth sets it per session. With `clone`, macOS's `copyfile(COPYFILE_CLONE_FORCE)` either shares blocks or fails, so on a server whose `version()` names Darwin berth always asks for a clone and reports `copy-on-write`. On Linux the clone is `copy_file_range`, which shares blocks on btrfs, and on XFS only when it was made with reflink, and copies in full anywhere else without a word, so berth asks for it only when it can see the server's data directory: the server is on loopback, `/proc/<backend pid>/cwd` is readable, its `postmaster.pid` names that directory and the server's port, and `statfs` says btrfs or XFS. On btrfs it reports `copy-on-write`. Whether an XFS has reflink can't be read without its tools or root, so there berth reports from what happened: the free disk `statfs` gives before and after the copy, `full copy` when the copy took half its size or more, `copy-on-write` when it took less, and the clone's own wording, copy-on-write only where the filesystem has it, for a copy under 32 MiB, where what the server writes meanwhile could pass for either. Where berth can see the directory on another filesystem, or can't see it, it leaves `file_copy_method` as the server has it and reports `full copy`, or, when the server is itself set to `clone` on a filesystem berth can't see, says the clone is copy-on-write only where the filesystem has it. A clone the server can't make (`XX000` or a `58` system error) is tried again with `copy`, reported as `full copy` with the server's reason in the entry's notes. `add --wait` prints the method beside the strategy, and `status --json` has it as `method`.
- **Kill recovery:** the copy's own backend pid and `backend_start` are saved on the entry as `copy_session` before the server starts copying. Whoever finds the clone process dead (`status`, `add`, `reset` through `liveState` and `lockClones`) ends that session with `pg_terminate_backend`, waits for it to go, then drops the target the record owns and clears `copy_session`, reading the login from the berth's own `.env` as `remove` does, so `status` never reads main's. A copy the server aborts leaves nothing; one it finished after the client died is a whole database the record owns, dropped the same way. Anything not settled stays on the entry: the next `add` or `reset` carries it to the new entry, and the clone process ends that session before dropping and copying again. `remove` and `prune` end any recorded copy session before their first drop.
- **Progress:** the server reports nothing while it copies, so a template entry has no total and `status` shows it `cloning` without a percentage. The source's size still feeds the disk warning, where the server's data directory is measured when the login may read `data_directory`, else the home and Docker Desktop disks as for MySQL.

The design states only that the copy is instant where the server's disk has copy-on-write and a full copy otherwise, and that `add` says which ran; when berth asks for a clone, and how it tells, are this record's and the user docs'.

## Options considered
- `pg_dump` piped to `psql`, or a copy through the driver: slow, needs client binaries or a second copier, and loses the server's instant clone; `template` is what the design names.
- Asking for `clone` on every Postgres 18 server: on ext4, including every Docker volume, `copy_file_range` succeeds as a full copy, so berth would report copy-on-write for a linear copy.
- Taking XFS as copy-on-write from its type alone: one made with `reflink=0` copies every block, and berth would say copy-on-write for it.
- Trying a reflink of berth's own on the server's filesystem: it needs a file berth may write on that filesystem, and the data directory is the server's.
- Judging the path by speed: a small database copies in milliseconds either way, and a fast disk copies a large one quicker than some clones finish their checkpoints.
- Reading `data_directory` to find the filesystem: only superusers and `pg_read_all_settings` may, and the login is neither.
- Ending whatever sessions it can under `disconnect` and failing on the rest: main's app would lose its sessions for a copy that can't happen.
- Waiting on the server's own five-second retry instead of listing sessions first: the server's error says how many sessions there are but not whose.
- Dropping the target from `status` right after marking the copy failed: while the server still runs the copy, its uncommitted database is invisible to `DROP DATABASE IF EXISTS`, and the copy then commits a database nobody drops; the session has to be ended first.
- Leaving the abandoned copy to finish: main's new connections would wait for a copy nobody wants, and Postgres 13 has no connection check to stop it.

## Evidence
`e2e/host_postgres_template_test.go`, against Postgres 13.22 and 18.1 in Docker with a login that is not a superuser, covers the copy holding main's rows and leaving main's checksums unchanged (the "source is never harmed" guarantee), a session on main failing that database while the others finish, `disconnect` announcing and then ending only the source's sessions, the announced pause on new connections, a full copy saying so, a killed copy dropping its database and `add` recovering, `status` showing `cloning`, `add --wait` and `reset`. `e2e/host_postgres_template_autovacuum_test.go` holds an autovacuum to one page per 100 ms on main's database, on 13.22 and 18.1; it failed, naming the worker as a session, before role-less rows were left out. `e2e/host_postgres_template_cow_test.go` runs against Homebrew's Postgres 18.6 on macOS with its data directory on APFS: a 1 GB database copied in 1.57 s, and 0.78 s on a second run, and `add --wait` reported `copy-on-write`. That server refuses to start ("postmaster became multithreaded during startup") in a shell with no valid locale, so the run had `LC_ALL=en_US.UTF-8` set. The btrfs and XFS paths ran in no test. Probes against `postgres:18.1` (Debian, aarch64 Linux) as a non-superuser with `CREATEDB`: `file_copy_method` has context `user` and values `{copy,clone}`; `SET file_copy_method = clone` and `CREATE DATABASE … STRATEGY FILE_COPY` succeed on its ext4 volume; another role's session shows `usename` and `application_name` with `client_addr`, `client_port`, `state` and `backend_start` null; `pg_terminate_backend` on a superuser's session is refused; `CREATE DATABASE` with a session on the source waits about five seconds, then fails with `55006`. Unit tests in `internal/postgres/template_test.go` cover no `STRATEGY` on 13 and 14, `FILE_COPY` reported as a full copy on 15 to 17, a clone asked for on macOS and on Linux only where btrfs or XFS is seen, an XFS clone reported from the disk it took, the message naming each session's application and address, never the login's role, and the `disconnect` refusal. The config's rules are tested in `internal/config`.

## Undoing it
The copy, session listing and method choice are `internal/postgres/template.go` and `localfs_*.go`; the clone-process side, the announcements and recovery are `internal/cli/templates.go`, wired through `clonedStrategy`, `prepareDumps` and `makeDatabase` in `dumps.go`, `liveState` and `lockClones` in `volumes.go`, and `dropDatabase` in `databases.go`; the entry fields `disconnect`, `copy_session` and `method` are in `internal/volume`; the config is `Disconnect` and `postgresStrategies` in `internal/config`. Reverting refuses `template` and `disconnect` in configs with exit `5` again; berths already made keep their template databases, which `remove` drops by the record as before. A clone state with `copy_session` set is ignored by older code, so end any copy still running on the server, and drop its target, before reverting.
