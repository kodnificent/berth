# 0051. Host Redis: key prefixes, the record and literal deletion

Status: accepted

## Context
A host Redis server is shared through key prefixes, under `[state.redis]` with `strategy = "prefix"` (design, Host Redis). The berth's prefix is its `{name}` and two underscores in front of main's, written to the key `prefix` names. No berth's prefix may begin another's or main's keys; a prefix with keys under it on any logical database is passed over; an empty main prefix is refused with exit `1`. `remove`, `prune` and `reset` delete every key under the recorded prefix on every logical database of the recorded server and nothing else, and `remove` and `prune` never need main's `.env`. Copying main's keys and Redis Cluster are out of scope. This record follows the shape of 0040 and 0047: the record decides, not the current config.

## Decision
- **Client:** berth speaks RESP2 itself, in `internal/redis`: commands go out as arrays of bulk strings, so any byte in a key, pattern or password reaches the server as it is, and replies are read with bounds on bulk and array lengths. It connects with a 10 second timeout and a minute per command, sends `AUTH [user] password` only when a password is set, then `PING`, so a server needing a login fails at connect. When the server answers `AUTH` by saying it has no password (Redis 6 and later: "called without any password configured"; older: "Client sent AUTH, but no password is set"), berth carries on without a login, as apps do with a stock `.env` holding `REDIS_PASSWORD=null`; the `PING` that follows must still succeed. The core never reads `null` as empty. Any other `AUTH` error refuses. Errors are scrubbed of the user and password as MySQL's are.
- **Server and login:** `from = "env:<PREFIX>*"` reads `<PREFIX>HOST` (required, else exit `5` naming `from`), `<PREFIX>PORT` (6379 when unset), `<PREFIX>USERNAME` and `<PREFIX>PASSWORD`. A URL key is refused with exit `5` in this version. `add` reads them from main's `.env`; `remove` and `prune` read the login from the berth's own `.env`, then the environment berth runs in, and connect with none when neither sets it; `reset` reads main's `.env` first, then those.
- **Config:** `strategy`, `from` and `prefix` are all required, and `prefix` is the only strategy; anything else exits `5`. The prefix key can't also be written by `[env]` or `[ports]`, or be the host database's prefix key, since berth writes a different value to each. `[state.redis]` sits beside `[state.mysql]` or `[state.postgres]`.
- **Prefix:** the segment is 0040's: `{name}` with every run of other characters than letters and digits turned into one underscore, none at either end, cut to 40. The prefix is the segment, `__` and main's prefix, so prefixes built from different segments never begin one another. A prefix that begins with main's (branch `app-x` beside main's `app_` gives `app_x__app_`) could hold a key main writes later, so such a candidate is passed over, and when the name's own segment is one, every candidate gets a first letter main's prefix doesn't start with (`b_app_x__app_`).
- **Choice under the lock:** in provision, under the registry lock, berth takes the first candidate, then `_2`, `_3` and so on, that no other berth's recorded prefix equals, begins or is begun by, and that has no key under it on any logical database. Every other berth's prefix counts whatever server its record names: `127.0.0.1`, `0.0.0.0`, a `.local` name or a DNS name can all be one server, and a prefix shared across two spellings would let one berth's removal delete the other's keys. Passing over a prefix held on another server costs only a `_2`. At most 1000 candidates are tried. The choice is saved in the record by the registry before the managed block is written, so a crash between the two leaves a record `remove` acts on. A later `add` keeps the recorded prefix, and refuses, exit `1`, when main's `.env` now names another server.
- **Record:** `redis` in the berth's record holds the server's host and port, the env key prefix, the segment, the prefix and its key. Never a login. The managed block sets the prefix key from the record, so `status`, `env` and `exec` show it without the server or main's `.env`.
- **Logical databases:** `CONFIG GET databases`, every one from 0 to its answer less one. When the server refuses `CONFIG` (renamed, or an ACL), `INFO keyspace`, every database it lists as holding keys. When it refuses that too, `SELECT` upward from 0 until the server refuses, at most 65536.
- **Literal deletion:** for each logical database, `SCAN` with `MATCH` set to the recorded prefix with every one of `*`, `?`, `[`, `]` and `\` escaped, and a star after it, `COUNT 1000`. Every key returned is compared byte for byte with the prefix, whatever the server's glob did, and only those that begin with it are deleted, with `UNLINK`, or `DEL` on a server that has no `UNLINK`. An empty prefix finds and deletes nothing, in the client and in the teardown, which also refuses a prefix other than the recorded one.
- **Teardown:** `remove` and `prune` list one `redis_keys` item, named by the prefix, when any logical database has a key under it, after databases and before files. When the server can't be reached or refuses the login, nothing is deleted and the record is kept. A failed key deletion is never read as already gone, as a missing file or volume is, since an error such as "no such host" would otherwise drop the record with the keys still on the server. When the deletion fails, the berth's `.env` is kept with the record, since the retry reads the login from it. `reset` deletes the same keys and lists the same item, and refuses, exit `1`, when main's `.env` names another server than the recorded one; with no server in main's `.env` it works from the record.
- **Status:** the prefix is shown as the managed key it is written to, `env REDIS_PREFIX feat_x__app_`.

## Options considered
- `github.com/redis/go-redis`: a large dependency with pooling, retries, Cluster and Sentinel berth doesn't use, for six commands. RESP2 is a few dozen lines, and owning it keeps every byte of a key and pattern in view.
- `KEYS <pattern>`: blocks the server for the whole key space, and still reads the prefix as a glob.
- `SCAN` without `MATCH`, filtering every key in berth: literal by construction, but sends every key of main's over the wire. Escaping keeps the server's filter and berth's comparison makes it safe whatever the server does with the pattern.
- Only databases 0 to 15: a server configured with more would keep a removed berth's keys there.
- `INFO keyspace` first: lists only databases holding keys, which suffices, but `CONFIG GET databases` is the server's own answer and doesn't depend on a report's format.
- One item per key in `remove`'s output: a cache can hold millions of keys.
- Allowing a candidate that begins with main's prefix: main's existing keys are checked, but a key main writes later could fall under it and be deleted with the berth.

## Evidence
`e2e/host_redis_test.go`, against Redis 7.4 in Docker published on a host port, covers the prefix guarantee with berths `feat`, `feat-x` and `feat-x-y`; deletion on logical databases 0, 1 and 15 by `remove`, `prune` and `reset`; a prefix with keys under it passed over; glob characters in keys and prefixes treated as text (main's prefix holding `[1]`, `?`, `*` and `\`); an empty main prefix refused; `remove` with main's `.env` deleted; and the prefix in `status`. Unit tests in `internal/redis` run against a fake server whose `SCAN` ignores `MATCH`, and cover keys not beginning with the prefix left byte for byte (binary keys too), the empty prefix deleting nothing, each way of listing logical databases, the `DEL` fallback, logins, and a refused login naming neither user nor password. `internal/names` has a fuzz test that prefixes stay clear of each other and of main; `internal/cli` covers a prefix held under a differently spelled host and what `remove` keeps when the deletion fails; `internal/config` covers validation.

## Undoing it
The client is `internal/redis`; the segment rule is `internal/names/redis.go`; the choice, env, teardown and reset in `internal/cli/redis.go`; the record type in `internal/registry`; validation in `internal/config/redis.go`. Records keep `redis` once written and older code ignores it, so reverting leaves those berths' keys on the server: delete them by the recorded prefix first, for each logical database, with `redis-cli --scan` and a literal prefix check. Moving to another client only touches `internal/redis`.
