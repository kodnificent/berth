# 0052. doctor --probe

Status: accepted

## Context
A berth's own host keeps its cookies apart from main's and every other berth's, until the app undoes it: a `Set-Cookie` with `Domain=.myapp.localhost` reaches every berth under that name, and a redirect built from a value still pointing at main sends the browser to main. Neither shows in env files or compose; only the running app's responses do. The design asks `berth doctor --probe` to request the berth's URL and each `[doctor] probe` URL at the loopback address with the berth's host, follow redirects within the berth, report cookies wider than the berth's host and redirects to main, report "not verified" when nothing answers, and never start anything (design, Doctor). The proxy judges the same cookies ([0054](0054-proxy-https-and-cookies.md)).

## Decision
- **Flag and checks:** `berth doctor --probe [path]`; without it no request is made. Three checks: `cookie_domain` (problem), `redirect` (problem) and `probe` (not verified). Problems exit `1`; not verified alone exits `0`, as in 0028. Findings gain an optional `fix`, left out of JSON when there is none.
- **Where:** in a berth only. In main, one `probe` not-verified finding says the checks are skipped because main has no berth to probe. In a worktree with no berth, and when the config is invalid (doctor's other checks then run on built-in defaults, which would probe the wrong URL), one `probe` finding says they are skipped.
- **What is requested:** the berth's URL as `status` gives it, then each `[doctor] probe` URL in order, each page at most once per run. Pages are told apart as a browser would: host in lowercase without a trailing dot, the scheme's default port left out, an empty path as `/`, no fragment; so `http://h:P` and a redirect to `/` are one request and one set of findings. A URL whose template names a port with no value yet is a `probe` finding, not requested.
- **Loopback only:** the transport's dialer ignores the host of the address it is asked for and always dials `127.0.0.1` at the URL's port over TCP4, so no name is looked up; the URL's host goes in the `Host` header and, for HTTPS, in SNI. `Proxy` is nil, so `HTTP_PROXY` and the rest are ignored. No cookie jar, userinfo stripped from every URL, so nothing the app sets goes back and no `Authorization` is sent. Bodies are never read: the body is closed as soon as the headers arrive.
- **What counts as the berth:** a URL is the berth's when its scheme is `http` or `https`, its host is the berth's host or a name under it (case and a trailing dot ignored) and its port, or the scheme's default, is one of the berth's assigned ports and not one of main's. Main's ports are checked first, so a port listed as both is main's: main's app is never requested, by the first URL or a redirect. Anything else is never requested. The berth's URL gets no exception: a URL on main's port is a `probe` finding saying the port is main's, and one on a port the berth wasn't assigned, such as the `80` the default `url = "http://{host}"` implies, is a `probe` finding saying the port is not the berth's, both suggesting `{port.<name>}`. Berth knows which ports it assigned but not everything main or another app listens on, so a port it didn't assign is never assumed to be the berth's.
- **`[doctor] probe`:** a list of URL templates with `{name}`, `{host}`, `{url}` and `{port.<name>}`, validated with the other templated keys (an unknown value or undefined port is a config error naming the file and `doctor.probe`). The loader also expands each with a sample name and refuses, as a config error, one that isn't an `http` or `https` URL on the berth's host or a name under it. At run time the same rule refuses the expanded URL again, and a URL on a port that isn't the berth's is a `probe` finding "not requested", since the loader can't know the ports.
- **Redirects:** `301`, `302`, `303`, `307` and `308` with a `Location` are followed, resolved against the page that sent them, while the target is the berth's as above, up to 10 per URL; beyond that, a `probe` finding names the page not checked. A target on main's host is a `redirect` problem located at the URL that sent it, naming the target, never requested; so is a target on main's port when its host is a name on this machine: the berth's host or a name under it, `localhost` or a name under it, or a loopback address. On those the scheme's implied port counts, so a redirect to `http://<berth host>/login` is to main when main publishes `80`. Another site's port says nothing about main: `https://idp.example.com:8000/` is neither followed nor reported, even with main on `8000`. A target on the berth's host refused for any other reason, such as a port berth didn't assign it (`https://<berth host>/` on `443`), is a `probe` not-verified finding at the URL that sent it, naming the target and why it was not requested, never silently dropped. Main's hosts are `localhost`, `127.0.0.1`, `::1` and the hosts main's `.env` sets in keys under `[env] url` and `[env] host`; main's ports are those main's compose project publishes and those main's `.env` sets explicitly in keys under `[env] url`, `[env] host` and `[ports]`. A port a URL only implies (`80`, `443`) is not main's, or every site would be. A redirect to any other host, such as an identity provider, is not followed and not reported: berth has nothing to check there and the app may mean it.
- **Cookie domain rule:** `cookie.Wider(host, c)` in `internal/cookie`: the cookie's `Domain=`, leading dot dropped and lowercased, is wider when the berth's host is strictly under it (`myapp.localhost` and `localhost` for `feat-x.myapp.localhost`). No `Domain=`, the berth's host, or a name under it is fine. A domain the host isn't under at all is not this finding: a browser refuses such a cookie, so it shares nothing. The finding is built by `cookieDomainFinding(location, host, cookie, env)` in `internal/cli`, apart from the HTTP client, so the proxy can report through the same type.
- **Fix:** when exactly one key in the berth's `.env` holds the wide domain (with or without its dot) and it is a name `[env.set]` accepts, `fix` is `{"config": "[env.set]\nKEY = \"{host}\"\n"}`: TOML to merge into the config, after which `berth add` writes the berth's host into that key. When several keys hold it, as `localhost` often is by `SESSION_DOMAIN`, `DB_HOST` and `REDIS_HOST` alike, there is no `fix` and the message names the keys without saying which should change: rewriting all of them would point the database at the berth's host name. The finding never carries the cookie's value, which may be a session secret.
- **Timeouts:** 10 seconds per request, connecting, TLS and headers included, so a hung app is a `probe` "did not answer within 10s" and doctor finishes. Ten rather than a few because dev servers that build a page on its first request take seconds.
- **HTTPS:** requested with certificate verification off. The connection only reaches this machine, the probe reads headers, not the certificate, and the proxy's local authority may not be trusted yet.
- **Location:** every finding's location is the URL as the user writes it, on the berth's host, never `127.0.0.1`.

## Options considered
- Letting `net/http` follow redirects with a `CheckRedirect` guard: the guard runs after the client has decided to follow; a manual loop judges each target before any request and records the page that sent it.
- Resolving `*.localhost` names: `getaddrinfo` on macOS may not, and a name resolving elsewhere would send the request off the machine.
- Also dialing `::1` when `127.0.0.1` refuses, for dev servers bound to IPv6 loopback only: not done: the probe dials `127.0.0.1` only; such an app is reported as not answering, never passed.
- A `probe` not-verified note for redirects outside the berth and not to main: an OAuth login would be flagged on every run for something that is right.
- A config error for a probe URL on a port that isn't the berth's: the loader doesn't know which ports `add` assigned, and `{port.<name>}` URLs are on them by construction.
- Refusing, rather than reporting not verified, when the config is invalid: doctor reports the config problems either way, and the rest of its checks still run.
- Reporting any `Domain=` that isn't the berth's host or under it: a browser drops a cookie for an unrelated domain, so it shares nothing across berths.
- Probing the berth URL's own port even when the berth wasn't assigned it: with the default URL and main publishing `80:80`, or a URL on main's port, the probe requested main's app and reported main's cookies as the berth's.
- A fix for every key holding the domain: retargets unrelated keys that share a host name.
- Adding the field to a separate wrapper type so existing findings stay four-field literals: two finding types for one list, where the proxy is meant to report through the one.

accepted, a redirect to main reported at the URL that sent it with main never requested, redirects within the berth followed with earlier cookies not sent back, nothing listening as one not-verified finding with exit `0` and nothing started, configured URLs requested with their host, the skip in main, and the fix for an env cookie domain. `e2e/doctor_probe_proxy_test.go` runs a fresh `berth doctor --probe` with every proxy variable pointing at a dead loopback port and sees the request reach the app, since `net/http` reads the proxy environment once per process and an in-process test can't show it (Go doesn't bypass the proxy for names under `.localhost`, so taking it from the environment fails that test). `internal/probe` covers requests to a `.invalid` host arriving at the loopback server (no DNS), URL credentials dropped, URLs outside the berth (other host, sibling suffix, other port, other scheme) never requested, main's port never requested even when listed as the berth's, redirects onto main's port or main's implied port reported and not followed, a redirect to another site that writes main's port ignored, a redirect to the berth's host on an unassigned port reported as unchecked, a protocol-relative redirect outside not followed, a URL whose berth host is only its userinfo refused, a page requested once however its URL is written, the redirect cap, a hung app, a never-ending body not waited for, and nothing listening. `internal/cookie` covers the domain rule, `internal/names` the label matching, `internal/config/probe_test.go` the loader's refusals and expansion, and `internal/cli/doctor_probe_test.go` a berth URL on main's port or an unassigned port never requested, the fix for one key, none for several keys or a key `[env.set]` refuses, no cookie value in a finding, and main's addresses.

## Undoing it
`internal/probe`, `internal/cookie`, `internal/cli/doctor_probe.go` and `internal/config/probe.go`; the `--probe` branches in `runDoctor`, `Doctor` in `Config` and its loop in `validate`, `names.Within`, and the `Fix` field on `finding` with the `nil` it adds to every other finding literal.
