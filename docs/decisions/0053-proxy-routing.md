# 0053. Proxy routing

Status: accepted; extended by [0054](0054-proxy-https-and-cookies.md), which adds HTTPS, the cookie checks and giving up root once the ports are bound

## Context
The design asks `berth proxy` to serve every berth's host, and every name under it, on a port-free URL: the request goes to the berth's port named by `[proxy] port`, or by `[proxy.routes]` for a listed name, with the `Host` header unchanged, `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-For` set and WebSocket upgrades passed through. It follows the registry without a restart, answers a host no berth has with a 404 listing the berths' URLs and a berth with nothing listening with a 502 naming it and its port, listens on loopback only, on 80 and 443 unless the user config sets `[proxy] http` and `https`, and where the system keeps those ports for administrators exits `1` with the command that allows it, never raising its own privileges (design, Hostnames, cookies and the proxy). This record covers routing and listening; HTTPS, its certificate authority, `proxy trust` and the cookie checks are in [0054](0054-proxy-https-and-cookies.md).

## Decision
- **Packages:** `internal/proxy` holds the route table, the handler and the listeners; `internal/cli/proxy.go` builds the table from the registry and each berth's config. Standard library only: `net/http/httputil.ReverseProxy` with `Rewrite`. No dependency is added.
- **Listening:** `127.0.0.1` and `::1` on `[proxy] http`, never a wildcard address. `::1` is skipped when the system has no IPv6 loopback, but a port taken or refused there fails the start like one on `127.0.0.1`. Before binding, `ports.Free`, the check `add` allocates with, probes the port on `0.0.0.0`, `127.0.0.1`, `::` and `::1`; when it finds a holder and the loopback binds still succeed, they are closed and the port is reported taken. Go sets `SO_REUSEADDR`, and macOS and Windows then let the more specific loopback bind through while another process holds the wildcard, so the proxy would silently take that process's local traffic. When the loopback bind itself fails, its own error decides between taken and reserved, since `ports.Free` counts a refused bind as held. The listeners open before the registry or any berth's config is read, so a start that fails has read and written nothing. `[proxy] https` is validated the same way (1-65535, not the same as `http`) and its listeners open the same way; what they serve is in 0054.
- **Ports from the user config only:** `[proxy] http` and `https` set in a personal or repository config are a config error naming the file and the key, since one proxy serves every repository and a project's value would be silently ignored. At start `berth proxy` reads only `[proxy] http` and `https` from the user config (`config.ProxyListenPorts`: the file's syntax, its keys and those two values), so it runs from any directory. The rest of the user config is the lowest layer of each project's config and is checked there: a user config holding `[proxy] port = "web"` or a route as a default for every project is valid, though only a project's own ports give it meaning.
- **Following the registry:** every 200 ms the proxy reads the registry with `registry.Peek`, which takes no lock and writes nothing (records are replaced by rename, so each one read is whole) and tells a record whose file is gone from one that is there but can't be read or parsed, and loads each berth's config as `berth add` would, from its worktree. The new table replaces the old one atomically; requests in flight keep the table they started with. A berth added is served within a second of `add` returning, and a removed one is gone on the next read. A berth that is recorded but can't be served keeps its host in the table and answers for it, so its names never fall through to a berth whose host encloses it, along with the browser's cookies for its host: an orphan, whose worktree git no longer has, gets the 404 and is left off its list, and one whose config fails to load gets a 502 naming the error. When the registry can't be read at all, the last good table is kept, since an empty one would answer every berth with the 404, and the error is said once on stderr each time it changes, not on every read. A record that is there but can't be read keeps that berth's entry from the last table, host and targets, which are still the berth's until its record is deleted, so its names never fall through for a tick; only a record whose file is gone drops its berth. A berth whose record has never been read has no host to keep.
- **Matching:** the `Host` header is lowercased, its port and a trailing dot dropped. A name belongs to the berth whose host it is, or is under at a label boundary (`names.Within`, as the probe uses); when berths' hosts nest, the longest host wins. Within that berth an exact `[proxy.routes]` name wins over `[proxy] port`. Route keys are templates of `{name}` and `{host}` that must expand to a valid hostname strictly under the berth's host, checked at load with a sample name, and their values, like `[proxy] port`, must name a defined port as `{port.<name>}` does.
- **Only the berth's ports:** a port name resolves only against the berth's recorded `assign` ports with a host port, through `PortValues`, so ephemeral, `none` and unrecorded ports are never routed. A port main uses is refused even though allocation already avoids main's published ports, because a berth keeps its ports while main's compose file can change. Main's ports are, as `add` reserves them, those every repository's main publishes, for every repository with a berth, plus those the berth's own main's `.env` sets in the `[env] url`, `[env] host` and `[ports]` keys the berth's own config names, as the probe reads them. The published ports depend only on the repository and are read again at most every 5 seconds per repository, since loading a compose project on every refresh would keep the proxy busy. A compose project that fails to load is never taken as publishing nothing: the last good read for that repository is kept, and with none, that repository's berths get a 502 saying main's compose project could not be read, said once on stderr. `berth add` fails on the same error for its own repository's main (`planCompose`) and skips another repository's main it can't read, so a berth there may already hold a port that main publishes; the proxy's refusal covers that case. The probe still treats a main it can't read as publishing nothing; the `.env` ports depend on the berth's config, so they are read for each berth on every refresh, which costs one small file. A refused berth, an invalid config, no `[proxy] port` or a port berth did not assign get a 502 page saying which, and the proxy says so once on stderr.
- **Compose warnings:** the proxy sends `logrus`, which compose-go logs through, to nowhere, or a warning about main's compose file, such as an obsolete `version`, would repeat every 5 seconds for as long as the proxy runs; `berth doctor` and `add` still print them. `logrus` was already in the module graph through compose-go; it is now a direct requirement, not a new dependency.
- **Forwarding:** the outbound request goes to `127.0.0.1:<port>`; when nothing answers there it is tried on `[::1]:<port>`, since dev servers that bind `localhost` may hold only the IPv6 loopback. Both are loopback and the same port. The transport ignores `HTTP_PROXY` and the rest, adds no `Accept-Encoding`, and has no response timeout, so a dev server building its first page and long polls are not cut off. `Out.Host` is the client's `Host`, port and all. Every header whose name starts with `X-Forwarded-` (`-Port`, `-Prefix`, `-Ssl`, `-Scheme`, `-Server` and the rest, not only the three `Rewrite` drops), and `Forwarded`, `X-Real-Ip` and `X-Original-Host`, is deleted, then `SetXForwarded` sets the three headers from what the proxy saw, so the app sees no origin a client claimed. Upgrades, WebSocket included, are `ReverseProxy`'s own.
- **Loopback peers only:** the handler refuses a request whose connection's remote address is not loopback, closing the connection without an answer, as a second fence behind the bind address: Linux with `route_localnet=1` and a DNAT rule can deliver another host's connection to `127.0.0.1`.
- **Pages:** small HTML, escaped by `html/template`, `Cache-Control: no-store`. The 404 lists every berth the proxy knows as `http://<host>`, with `:<port>` when the proxy is not on 80, and names the requested host without a scheme. The 502 names the berth, the port and the dial error, and says the proxy starts nothing.
- **Failing to listen:** exit `1` with a message naming the port, and for a refused port the address, and `next` lines. Taken: the command that names the holder (`lsof -nP -iTCP:<port> -sTCP:LISTEN`, or `netstat -ano -p tcp | findstr :<port>` on Windows) and the user config to change. Refused:
  - Linux: ports below `net.ipv4.ip_unprivileged_port_start` (1024 by default; the message reads the current value) are root's. The hints are `sudo sysctl -w net.ipv4.ip_unprivileged_port_start=<port>`, until the next boot, a file in `/etc/sysctl.d` to keep it, or `sudo setcap cap_net_bind_service=+ep <path to this berth>`, which lasts until the binary is replaced. `sudo berth proxy` is not offered: sudo resets `HOME` there, so the proxy would read root's registry and serve no berths.
  - macOS: the 10.14 change that let unprivileged processes bind ports below 1024 covers the wildcard address only; on `127.0.0.1` and `::1` they are still administrators' (see Evidence), and the proxy may not use the wildcard. So the hint runs the proxy as an administrator: `sudo env HOME=<home> [XDG_STATE_HOME=..] [XDG_CONFIG_HOME=..] [BERTH_STATE_DIR=..] <path to this berth> proxy`, carrying `HOME` and whichever of the others are set, quoted for the shell. sudo's `env_reset` drops the `XDG_` and `BERTH_` variables, whether it keeps `HOME` is the sudoers policy's choice (unreadable to an ordinary user, so not assumed), and `secure_path` may not hold berth's directory; without them the proxy would read another registry and serve no berths. `env` sets them as the command root runs, so no sudoers `setenv` right is needed. Run that way, root only binds the ports: the proxy then gives root up for good before it reads the registry or writes anything (0054), so it leaves nothing root-owned in the user's state directory.
  - Windows has no privileged ports; `WSAEACCES` means the port is in a range the system reserves (Hyper-V, WSL, Docker) or another socket holds it with `SO_EXCLUSIVEADDRUSE`. The hint names `netsh interface ipv4 show excludedportrange protocol=tcp` and the `netstat` line.
  - Every system: or set `[proxy] http` in the user config to a port above 1023, which the URLs then carry.

## Options considered
- Binding the wildcard address and refusing non-loopback peers in the handler: on macOS it would make port 80 work without sudo, but a second interface would accept connections at all, which the guarantee forbids.
- Following the registry with file notifications: needs a dependency (`fsnotify`) or one watcher per platform, and a 200 ms read of a few small files meets the one-second bound.
- Reading the registry under its lock: every refresh would contend with `add` and `remove`; records are written by rename, so a lock-free read sees each whole.
- Keeping a berth's last good routes while its config is invalid: the user would see the old app with no sign their edit broke the config.
- Defaulting `[proxy] port` to a berth's only assigned port: that port may be a database's, and the proxy would send a browser there.
- Answering a host no berth has with a bare 404 unless it is a name on this machine, so a page that rebinds its DNS to `127.0.0.1` can't read the berths' names: the design lists the berths on every 404, browsers resolve `.localhost` themselves, and what leaks is the berths' names, not their apps, which still need their own host.
- Dialing only `127.0.0.1`, as the probe does: a dev server on `::1` alone would be a 502 though it is running on the berth's own port.
- Checking for a wildcard holder after binding the loopback: the proxy's own sockets would then make every port look held.
- `sudo -E berth proxy`: sudoers often forbids `-E`, and it hands root the whole environment rather than the variables that find the registry.
- pf redirects from 80 to a high port on macOS, as some local proxies install: a firewall rule change berth would have to explain and undo, and it covers `127.0.0.1` and `::1` with separate rules.

## Evidence
`e2e/proxy_test.go` covers routing of the berth's host and names under it to its web port, the forwarded headers, a routed name sent to another of the berth's ports, a berth added and one removed while the proxy runs, the 404 page listing the berths' URLs, a WebSocket both ways, no TCP connection at all on the machine's other address, the 502 pages for nothing listening and for no `[proxy] port`, listen ports in a project config refused with exit `5`, a taken http port and, on Linux as a user other than root, the hint for a reserved port. `internal/proxy` covers matching at label boundaries ignoring case, port and a trailing dot, routed names, nested hosts, every forwarded header a client sent removed, a non-loopback peer getting a closed connection and no answer (through a real server whose connections claim a non-loopback peer), an app on `::1` alone reached, a port held on the wildcard address counted as taken, only loopback addresses bound, and each system's hint for a refused port. `internal/cli/proxy_test.go` covers, over a registry on disk, routes going only to assigned ports and never to one any repository's main uses, an orphan nested in another berth's host, a berth whose config fails to load, the last table kept when the registry or one record can't be read, the last good read of main's published ports kept, each failure said once, and a refresh writing nothing to the state directory. `internal/config/proxy_test.go` covers routes outside the berth's host, undefined port names, and listen ports refused outside the user config. On macOS 26.5 as an ordinary user, `net.Listen` on `127.0.0.1:80`, `[::1]:80`, `127.0.0.1:443` and `127.0.0.1:1023` fails with `permission denied`, while `0.0.0.0:80` and `[::]:80` succeed.

## Undoing it
