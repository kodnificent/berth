# 0054. Proxy HTTPS and cookies

Status: accepted

## Context
The design asks `berth proxy` to serve HTTPS that browsers trust and to keep cookies inside each berth (design, Hostnames, cookies and the proxy). It signs a certificate for each name it serves from a local certificate authority in berth's state directory, readable only by the user, that can vouch only for names under `.localhost`; `berth proxy trust` adds it to the system's trust store through the system's own prompt and `untrust` removes it, berth never trusting it on its own; `trust` prints how to add it to Firefox. It reports every `Set-Cookie` whose `Domain=` covers more than the berth's host, in its output and to `berth doctor` without `--probe`; a domain of the berth's host or under it passes untouched; `[proxy] cookies = "rewrite"` replaces a wider domain with the berth's host; cookies are never renamed or stripped. The guarantee "The proxy is local" says a certificate the authority signs for any other name fails verification. 0053 built plain HTTP and left the https port read but unused.

## Decision
- **Packages:** `internal/authority` (the authority and the leaf issuer), `internal/truststore` (trust and untrust, one file per system), `internal/cookie` (reading and rewriting the raw header, and the record of what the proxy saw, beside the existing `Wider`), `internal/privilege` (giving up root), `safefile.Write`, `internal/cli/proxy.go` and `proxy_cookies.go`. Standard library crypto only; no dependency is added.
- **The authority:** `<state>/proxy/ca/cert.pem` and `key.pem`, an ECDSA P-256 key in PKCS#8 PEM and a self-signed certificate valid ten years, `IsCA`, path length zero, key usage certificate and CRL signing, and extended key usage `serverAuth` only: Go checks extended key usages at every certificate of a chain, the root included, as the system verifiers do, so a leaf it signs for email protection, code signing or client authentication fails for that use. Name constraints, marked critical so a client that can't read them refuses the authority: permitted DNS subtree `localhost` only (which RFC 5280 and Go read as `localhost` and every name under it); excluded IP ranges `0.0.0.0/0` and `::/0`, so no leaf for an address verifies; permitted email domain `localhost` and permitted URI domain `localhost`, so a leaf naming any other mailbox or URI fails whatever usage is asked. One case no CA can close in Go: a verifier asking for `ExtKeyUsageAny` skips usage checks, and a leaf with no names at all meets no name constraint, so it verifies; a verifier asking for any usage has asked for nothing in particular.
- **Making it:** in a fresh directory from `os.MkdirTemp` (mode `0700`) under `<state>/proxy`, the key created with `O_CREATE|O_EXCL` and mode `0600` from the first byte, never wider and then narrowed, then the directory renamed to `ca` whole. A reader never sees a certificate without its key, and of two processes making one at once the first rename wins; the loser's rename fails on the existing directory and it loads the winner's. The key is never logged, printed or sent: no code path formats it.
- **Loading it:** refused, with exit `1` and how to replace it (`untrust`, delete the directory, and berth makes a new one; `trust` again after), when the key's mode gives its group or others any permission at all, read, write or execute (it may have been copied or changed, so berth does not quietly narrow it), when the key doesn't match the certificate, when the certificate lacks any limit above, checked exactly: `IsCA` with valid basic constraints, `MaxPathLen` 0 with `MaxPathLenZero`, extended key usage `serverAuth` alone, critical constraints, permitted DNS `localhost` alone with none excluded, no permitted IP ranges, excluded ranges covering all of IPv4 and IPv6, permitted email and URI `localhost` alone (so an authority put in its place that could vouch for more is never used), or when it has expired. An authority without the usage, email and URI limits fails this check, and the message says it was made by an earlier berth or put there by something else; replacing it is the whole migration. Windows keeps no permission bits; the key there has its directory's ACL, the user's profile.
- **When it is made:** by `trust`, or by the proxy's first start. Run as the user, the proxy makes it after checking both ports are free with `ports.Free`, and before opening either listener, so the https port never accepts a connection without it, and a start that fails on a port (taken or reserved) has written nothing. If the ports looked held but the listeners still opened (the holder left between the two checks), it is made after listening. Run as root, it is made after the listeners are bound and root given up, below: a connection that arrives in between waits in the listen queue and its handshake runs once the authority is loaded.
- **Running as root:** the macOS sudo hint from 0053 runs the proxy as root, and the proxy now writes the authority and the cookie record. Root only binds: as root the proxy reads the user config's two ports, checks and binds both listeners, and then, before it reads the registry, any project config, the authority or the cookie record, gives root up for good (`privilege.Drop`): it becomes the user `SUDO_UID` and `SUDO_GID` name, which sudo sets for the command it runs and `env` in the hint passes on, with supplementary groups reduced to that user's primary group (`setgroups`, then `setgid`, then `setuid`, which as root sets the real, effective and saved ids alike), then checks the ids, that the supplementary groups are only that group, and that `setuid(0)`, `seteuid(0)` and `setgid(0)` all fail. It then refuses, exit `1` and serving nothing, a state directory that exists and is owned by anyone else. Root with no `SUDO_UID`, or one naming root, or a drop or check that fails, exits `1` the same way. Everything after is written as the user, so the state directory never holds a file the user can't replace, and no code changes an owner or mode by path as root, which a local process could otherwise point at a root file with a link. `berth proxy trust` and `untrust` refuse to run as root, whatever the store, `BERTH_TRUST_STORE` included, since they work on the user's state directory and call `sudo` themselves where the system needs it; no test needs them as root. `privilege.Drop` honours `SUDO_UID` only when the real uid is 0 as well as the effective one, so a setuid-root berth, whose caller sets those variables, is refused. Windows has no root to give up and keeps no ports for administrators, so the proxy never needs elevation; run elevated anyway it stays elevated, writes into the user's profile, whose inherited ACL keeps the files the user's, and changes no ACL or owner.
- **Leaves:** one per name, signed on the first handshake for it from `GetCertificate`, valid 30 days, signed again when less than a day is left, `serverAuth`, the name as the only DNS SAN. Every leaf shares one P-256 key made at start in memory and never written. A name gets a leaf when it is a valid lowercase hostname that is `localhost` or under it, whether or not a berth has it, so a mistyped berth name over HTTPS reaches the 404 page that lists the berths instead of a TLS error. Any other name, an IP address or no SNI at all gets no certificate and the handshake fails. The cache holds at most 1024 leaves, dropping the oldest, so a client asking for endless names costs signing time, not memory.
- **Listening:** the https port opens exactly as the http port (0053): `127.0.0.1` and `::1` only, after `ports.Free`, with the same exit `1` and hints, now naming `[proxy] https` for that port. `[proxy] http` equal to the https port, set or default, is a config error. Connections to the https port from a peer that isn't loopback are closed by the listener before any handshake, as well as by the handler's check. HTTP/2 is offered: Go's server leaves extended CONNECT off (`disableExtendedConnectProtocol` in `net/http/internal/http2`), so browsers open WebSockets on a separate HTTP/1.1 connection, which `ReverseProxy` passes through. TLS 1.2 is the minimum. Handshake errors are not logged: an untrusted authority makes every browser handshake fail until `trust`. The 404 page over HTTPS lists `https://` URLs on the https port.
- **`BERTH_TRUST_STORE`:** when set, `trust` and `untrust` use only the store it names, raise no prompt and need no administrator. macOS: a keychain file; `security add-certificates -k <file>` adds the certificate with no trust settings, `security find-certificate -a -Z <file>` lists its SHA-256 fingerprints, `security delete-certificate -Z <SHA-256> <file>` removes it (`security help delete-certificate`: "by its SHA-256 (or SHA-1) hash value"). Linux: a directory standing in for the system's CA directory; `trust` writes `berth-proxy-<first 16 hex of SHA-256>.crt` with `O_EXCL`, `untrust` deletes that file only while it still holds exactly that certificate. Windows: a CurrentUser store's name; `certutil -user -addstore <name>`, `certutil -user -store <name> <SHA-1>` to see it is there and `certutil -user -delstore <name> <SHA-1>`, certutil taking no other fingerprint.
- **The system's store, without the variable:** macOS: `security add-trusted-cert -r trustRoot -p ssl -k <login keychain>` (user trust settings, no `sudo`; macOS raises its authorization dialog), the keychain from `security login-keychain`. `-p ssl` limits the trust settings to the SSL policy, server authentication; `security help add-trusted-cert` lists `-p policy` with `ssl, smime, codeSign, IPSec, iChat, basic, swUpdate, pkgSign, pkinitClient, pkinitServer, eap`. `untrust` checks the keychain holds the SHA-256 (`security find-certificate -a -Z`) and runs `security delete-certificate -Z <SHA-256> -t <login keychain>`, which removes its trust settings too. Linux: the first of `/usr/local/share/ca-certificates` (`update-ca-certificates`), `/etc/pki/ca-trust/source/anchors` (`update-ca-trust extract`), `/etc/ca-certificates/trust-source/anchors` (`trust extract-compat`) and `/usr/share/pki/trust/anchors` (`update-ca-certificates`) that exists with its command on `PATH`; `sudo install -m 0644 /dev/stdin <dest>` with the certificate's bytes on its standard input, so no file the user can write stands between berth's check and root's copy (a process of the same user could rewrite such a file while `sudo` waits for the password, and root would install it); then berth reads the destination, in a root-owned directory, and when it does not hold exactly the recorded certificate runs `sudo rm -f` on it and fails without rebuilding the bundle, since the path was free just before; only then `sudo` the update command (no `sudo` when already root). `sudo` asks for the password on the terminal, not standard input. A file of that name already there is refused, never overwritten; `untrust` checks the recorded file still holds the certificate, then `sudo rm -f` and the update. Windows: `certutil -user -addstore Root`, which raises Windows's own confirmation, and `certutil -user -delstore Root <SHA-1>`; `CRYPT_E_NOT_FOUND` (`0x80092004`, printed in every language) counts as not there, and so does `NTE_NOT_FOUND` (`0x80090011`), which certutil returns for a named store that was never created; the first Windows run of the throwaway store showed it. Narrowing: only macOS takes a trust narrower than the certificate. The Linux bundles trust each anchor for every purpose, and certutil's `-addstore` sets no purpose on a Root certificate, so there the authority's own extended key usage and name constraints are the narrowing; Windows CryptoAPI and the Linux TLS stacks honour both. Other systems: `trust` exits `1` saying berth doesn't know the store. The tools never get berth's stdin (0003): a prompt is the system's, on its own window or terminal. `security add-trusted-cert`, `security add-certificates` and `certutil -addstore` take only a certificate file (`security help add-trusted-cert`: `[certFile]`; `add-certificates [-k keychain] file...`; certutil's `-addstore CertificateStoreName InFile`), so on macOS and Windows berth writes the bytes to a fresh temp file only the user can read (`os.CreateTemp`, `0600`, deleted after) and passes that. The window is accepted there: the tool runs as the user, not as root, and reads the file at once; a process of the same user that rewrote it in between could as well run the tool itself and raise the same system prompt, and berth's after-add check by SHA-256 then fails.
- **Write-ahead record, by fingerprint:** `<state>/proxy/trusted.json` lists, per store (`BERTH_TRUST_STORE`'s value, empty for the system's), the SHA-256 berth matches by, the SHA-1 only for certutil, and for a directory store the file it writes. `trust` writes the entry, marked `adding`, before touching the store; then hands the store's tool the certificate's bytes berth checked, never the path in the state directory, which could change after berth checked it (on standard input on Linux, a private temp file elsewhere, above); then checks the store holds that SHA-256, failing if not; and only then clears `adding`. For a directory store the entry is also marked `placed` right after berth sees its path free and before it writes there, so whatever lands at that path is berth's to remove, even content that is not its certificate; `placed` is cleared with `adding`. A failure at any step, a cancelled dialog, a failed `update-ca-certificates`, leaves the entry, so `untrust` can remove what was added and a second `trust` runs the steps again and finishes; each step is safe to repeat (on Linux the copy is skipped when the file already holds the certificate and the rebuild always runs). `trust` with a finished entry and the store still holding it says the authority is already trusted. `untrust` marks an entry `removing` before removing it, so a failure part way is finished by the next `untrust`; an entry is reported as not found, removed elsewhere, and forgotten only when its recorded place holds nothing of berth's: on Linux the recorded file is absent, on macOS and Windows no certificate with the recorded fingerprint is in the store. A file at berth's recorded path with other content is removed when the entry is `placed`, and otherwise is neither removed nor counted as gone: `untrust` names the path, keeps the record and exits `1`; a second `trust` likewise removes a placed one and installs afresh, and refuses, naming the path, one berth did not place; with nothing recorded it says so and exits `0`. Untrusting needs only the record, so it works after the authority's directory is deleted. On Linux, before any delete, and as root before `sudo rm`, the recorded file must be in one of the known anchor directories (or the throwaway directory), named `berth-proxy-<16 hex>.crt`, and hold exactly the recorded certificate; anything else is refused with the reason.
- **What `trust` prints:** the authority's path and the store, then how to import it into Firefox (Settings, Privacy & Security, Certificates, View Certificates, Authorities, Import, the path, "Trust this CA to identify websites"), and on Linux the NSS `certutil` line for Chrome and Chromium, which read `~/.pki/nssdb` rather than the system store. The proxy prints at start that browsers warn until `berth proxy trust` when the record holds no entry for the current store.
- **Cookies:** `ReverseProxy.ModifyResponse` reads each `Set-Cookie` itself, as a browser does (`cookie.NameAndDomain`): the name is the text before the first `=` of the first segment, the domain the value of the last `Domain` attribute that has one. `http.ParseSetCookie` is not used: it refuses names and values browsers store, such as `cart[items]=3`, `prefs={"theme":"dark"}` and `name=café`, which would pass unjudged. The value is never extracted. The name and domain, now unchecked text from the app, are made printable (any rune `unicode.IsPrint` refuses, and invalid UTF-8, becomes `?`) and cut on a rune boundary to 128 and 255 bytes before they are printed or recorded. Each is judged with `cookie.Wider(berth host, cookie)`, the probe's rule (0052), against the host of the berth the request matched, so a cookie set by a `[proxy.routes]` name is judged and rewritten against the berth's host like any name under it. A cookie whose domain is unrelated to the host is not wider, so it is neither reported nor rewritten: a browser refuses it, and it shares nothing. With `rewrite`, `cookie.RewriteDomain` replaces the value of each `Domain` attribute that is wider with the berth's host and leaves every other byte of the header as the app sent it; a header that isn't wide is never touched. Wide cookies are reported under `rewrite` too.
- **Reporting:** the proxy says each wide cookie once per run per berth, name, domain and outcome, on stderr: `berth proxy: <berth>: cookie <name>, set by <page>, has Domain=<domain>, so a browser sends it to every berth under <domain>; ...`. The page is the request's scheme, host and path, never its query, which may hold a token.
- **What doctor reads:** `<state>/cookies/<berth id>.json`, a JSON list of name, domain, page, whether it was rewritten and when, never the value. A wide cookie replaces what the list held for that name; a `Set-Cookie` of that name that isn't wide removes it, since the app now scopes it to the berth; the list holds at most 64 names (dropping the oldest), names cut to 128 bytes and pages to 512. The proxy writes only when the list changes, from one goroutine fed by a 1024-entry queue that drops when full, so a response never waits on the disk or the registry lock. Each write runs under the registry lock and only while the berth's record exists (`registry.IfRecorded`), which opens the existing lock and never creates it; `remove` and `prune` delete the file with the berth's other state (`cookie.Forget` beside `lastuse.Forget`) under that lock, so a response in flight at removal never leaves it behind. `berth doctor` without `--probe` turns each entry into the probe's `cookie_domain` problem through `cookieDomainFinding`, with its `fix`, located at the page, plus when the proxy saw it and whether it rewrote it. Doctor makes no request for it.

## Options considered
- A certificate per berth with a wildcard for the names under it: one leaf for many names, but a wildcard covers one label only, so `api.app.feat-x.myapp.localhost` would need another, and a name outside every berth would get none for the 404 page.
- Leaves only for registered berths' names: an HTTPS request for a mistyped name would fail its handshake rather than show the list of berths the design promises on the 404.
- Narrowing a key found with a wider mode to `0600`: hides that it may have been copied while the authority stays trusted.
- Keeping the cookie record in memory and having doctor ask the proxy: doctor would need the proxy running and a socket berth must secure; a file survives a proxy restart.
- A per-berth record written on every response: a busy app would rewrite it constantly; it changes only when a cookie's verdict does.
- Chowning what the proxy writes as root to the state directory's owner: as root it changed owners and modes by path inside a directory the user controls, where a link swapped in could aim it at a root file.
- Requiring the authority to exist and writing nothing as root, without dropping: the proxy would still read the user's configs and registry as root, and doctor would lose the cookies under sudo.
- `http.ParseSetCookie` with a fallback: two readings of one header, and the fallback is the one that must be right anyway.
- A private temp file for root's `install` on Linux: the same user could rewrite it while `sudo` waited, and root would install the swap system-wide.
- Recording trust after adding: a failure between the two leaves a trusted certificate berth doesn't know it added.
- HTTP/1.1 only on the https port: a dev server serving hundreds of modules would be held to six connections per host by the browser.
- `security add-trusted-cert -d` (admin trust settings): needs `sudo`; user trust settings are what the user's browsers read.
- `security add-trusted-cert` for the throwaway keychain: it changes trust settings, which the test must see unchanged. Its `-o settingsFileOut` writes them to a file instead, but whether it then raises the authorization dialog is not documented, so it was never run.
- Matching the certificate to remove by its subject name: a user's own certificate of the same name could go.
- Rewriting the parsed cookie with `http.Cookie.String()`: Go reorders and normalizes attributes, so `SameSite`, case and unknown attributes would change; only the `Domain` value may.
- Reporting a cookie whose domain is an unrelated site: browsers drop it, so nothing is shared.

## Evidence
`e2e/proxy_https_test.go`: both names verify against the authority as the only root, `X-Forwarded-Proto: https`, a WebSocket both ways over TLS, a leaf the test signs for `example.com` and one for `203.0.113.7` fail verification, a handshake for `example.com` or `feat-x.myapp.localhost.example.com` gets no covering certificate, and the key's mode is `0600`. `e2e/proxy_https_local_test.go`: no HTTPS connection on a non-loopback address. `e2e/proxy_trust_test.go`: on macOS a throwaway keychain holds the authority after `trust` and is as before after `untrust`, with `security dump-trust-settings` (user and admin) and the user's keychain search list unchanged; `trust` prints Firefox and the certificate's path. `e2e/proxy_cookies_test.go` and `e2e/proxy_cookies_remove_test.go`: `.myapp.localhost` and `localhost` reported by the proxy on one line with the domain and by `doctor --json` and text, never the value, with no request to the app; with `rewrite` the jar sends the cookie to the berth's host and names under it, never to another berth; the berth's own domains pass byte for byte in both modes and are not reported; `berth remove` leaves no record of the cookie; and doctor forgets a wide cookie once the app scopes it to the berth.

Unit tests: `internal/authority` (leaves verify, other names and IPs don't, the cache bound, renewal near expiry, a key at `0644` refused and left at `0644`, one case per limit `Load` checks, and leaves for a mailbox, code signing and a client URI failing); `internal/privilege` (root with no sudo user, a setuid-root berth and a state directory of another user refused; as root, in a child process, every id becomes the sudo user's and `setuid(0)` fails; a drop that leaves root recoverable is caught); `internal/cookie` (the rewrite changes only wide `Domain` values, byte for byte otherwise; the record's bound; control characters replaced); `internal/proxy/cookies_test.go` (the three headers Go can't parse are reported and rewritten; a non-loopback peer gets no TLS handshake); `internal/cli` (what doctor reads, nothing written for a berth with no record, the proxy binding as root then serving as the sudo user, `trust` and `untrust` refused as root); `internal/truststore`, over a store in memory on every system, and on Linux over the system store's code with a directory of the test's as the anchor and root's commands run as the user, including a same-user rewrite of every file argument before each command, a mismatch after install removed with the bundle not rebuilt, and a foreign file at berth's path never counted as gone.

In an Alpine container, the Linux berth binary run as root with `SUDO_UID` and `SUDO_GID` set showed that user's uid and gid for every id, and one group, in `/proc/<pid>/status` while serving, and made the authority owned by that user with the key at `0600`; with no `SUDO_UID`, or a state directory owned by another user, it exited `1` and wrote nothing; `berth proxy trust` as root exited `1`. Go's rule for any usage was checked by hand: a code signing leaf with no names verifies for `ExtKeyUsageAny`. A manual run showed an HTTP/2 client served over the https port.

Not exercised: the system's own store, without `BERTH_TRUST_STORE`, on any platform. The macOS login keychain, the Linux CA directories with `sudo` and the Windows Root store were written from `security help`, the distributions' documentation and `certutil`'s, since each run would change a machine's trust or raise a prompt. `security add-trusted-cert -p ssl` and `install -m 0644 /dev/stdin` under `sudo` on a real system were never run; piping into `install -m 0644 /dev/stdin <dest>` was checked with BusyBox 1.37 and GNU coreutils 8.32 in containers, as root. Giving up root is shown on Linux only: macOS's `setuid` is the same POSIX call but was not run there, and Windows elevated was not run. The root tests skip on a developer's machine. The Linux CI jobs are set up to run them: the unit job runs every `TestAsRoot` test through `sudo` with `BERTH_TEST_ROOT=1`, which turns a skip into a failure, and fails unless at least six pass, and the e2e job sets `BERTH_E2E_SUDO=1`, so one test starts the proxy with `sudo -n` on ports below 1024 and checks the serving process's ids and the owner of everything under the state directory. The Windows and Linux throwaway stores run only in CI.

## Undoing it
`internal/authority`, `internal/truststore`, `internal/privilege` and `dropRoot` with `refuseRootTrust` in `internal/cli/proxy.go`, `internal/cookie/rewrite.go` and `seen.go`, `internal/safefile/write.go`, `internal/cli/proxy_cookies.go`, `registry.IfRecorded`, `cookie.Forget` in `remove`'s forget list, `proxyCookieFindings` in `runDoctor`, `Cookies` and `RewritesCookies` in `internal/config/proxy.go` with `ProxyListenPorts` (which replaced `ProxyListenPort`), `ListenFor` and `LoopbackOnly` in `internal/proxy`, the `ID`, `RewriteCookies`, `HTTPSPort` and `Cookies` fields and `judgeCookies`, and `runProxy`'s https listener, authority and `trust`/`untrust` branches. A user who trusted the authority runs `berth proxy untrust` first; the state directory's `proxy` and `cookies` directories can then be deleted.
